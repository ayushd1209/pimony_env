01 / The main result

The CPU does much less work moving weights.

For a single input vector, the CPU baseline brings the matrix weights to the processor. pim.gemv lets the memory-side engines perform those dot products where the weights reside.

The host still prepares the vector, maintains cache visibility, submits the work, waits for completion, and reads the results. Those costs are included in the measured matmul sections.

On the simulated O3 host, those complete matmul sections take 69.58 µs with pim.gemv, versus 1,064.77 µs with the OpenBLAS baseline.

This is the strongest comparison to lead with: the six linear projections, including their surrounding offload work, on the same host configuration.

On gem5's in-order Minor core the same projections give 16.54×, against 17.53× on O3 when both cores have the same vector unit: on BERT-base, out-of-order execution adds 6–12%. On GPT3-2.7B the order flips, 28.29× on Minor against 22.81× on O3, so the host comparison depends on the workload. Section 06 has both.

Here, “end to end” means the timing path from host preparation through result consumption inside one encoder layer. PIMony models timing and traffic; it does not calculate the numerical GEMV outputs.

Evidence: first eight phase blocks in the OpenBLAS O3 statistics and PIM O3 statistics. Calculation explained in section 04.

02 / The workload

Six projections become eight PIM jobs.

A GEMV is a matrix–vector multiplication. Each output is a dot product between one row of weights and the input vector. The host adds the bias.

y[o] = b[o] + Σᵢ W[o, i] · x[i]

The benchmark executes one BERT-base encoder layer, with hidden width 768 and feed-forward width 3,072. With batch 1 and sequence length 1, its six projections are GEMVs.

ProjectionMatrix: outputs × inputsPIM jobsDot steps / job

W1: expand3,072 × 768148

Total7,077,888 weights816 FP16 inputs per step

Why three jobs for W2? One PIM dot product fits at most 1,024 input elements in a DRAM row. W2's reduction length is 3,072, so software splits it into three 1,024-element pieces. The CPU loads and sums the three partial results for every output.

Attention, GELU, residual additions, and LayerNorm stay on the CPU. The input vector is staged four times per layer: once shared by Q/K/V, then once each for Wo, W1, and W2.

How the weights fit into memory

The useful FP16 weights occupy 14,155,776 bytes (13.5 MiB). The PIM layout pads rows, giving 16.5 MiB of weight-array storage before gaps between arrays. Its 768-element dots use 48 of 64 row steps. W2 fills its three rows completely.

The older “28 MB of weights” description corresponds to FP32 storage. It is not the useful FP16 weight size in this comparison. Weight initialization and layout are outside the timed region.

Source: bert.c, dimensions, pim_idx, PIM_PARTS, WDIM0, and bert_layer.

03 / The complete path

Offload has a beginning, a middle, and a return path.

Reading “PIM compute time” alone would omit much of the real work. The measured projection sections include the following sequence.

  1. Host CPU

    Stage the input vector.

    Convert FP32 activations to FP16 and store one copy per channel. Each of the four channels needs a locally accessible copy. Q/K/V reuse the same staged vector.

  2. Host caches → DRAM

    Make the input visible.

    pim.fence.cl cleans the dirty vector lines: 672 operand lines across the layer. The program also cleans each job's descriptor, which contains the weight, vector, and output addresses.

  3. Instruction → memory front end

    Submit one shaped job.

    pim.gemv supplies the descriptor pointer, output count, and dot-step count, and returns a completion token. Fetching the descriptor is timed. Software then calls pim.wait.

  4. Memory-side sequencer

    Fill the global buffers and schedule the dots.

    Four D2GWRITE commands load the channel buffers. The sequencer distributes MAC commands over 32 bankgroup streams: 4 channels × 2 ranks × 4 bankgroups. Each stream drives four banks. Busy-stream and queue checks control when another command may issue.

  5. PIM readout → result memory

    Drain and write back.

    One READRES drains a bankgroup's results. The model schedules one write per MAC command, with four FP16 results as its logical payload. Pending readouts and result writes participate in the completion condition.

  6. Interrupt → host CPU

    Complete the token and wake the host.

    The completion interrupt reaches the trap handler. It reads the done mask and publishes the completed token to the CPU scoreboard. pim.wait can then finish. There are eight measured sleeps per layer.

  7. Host CPU

    Invalidate, load, convert, and combine.

    The host invalidates the output range, loads FP16 partials, converts them to FP32, and adds bias. W2 combines three partials per output. The CPU then continues with the next layer operation.

The measured speedup already pays for this round trip. It excludes the one-time weight initialization/layout and benchmark startup, and includes the repeated per-layer work above.

Two details of the completion contract

Result writes complete when accepted by the posted-write path, not necessarily when the DRAM array has been updated. Matching reads rely on the memory model's queued-write behavior. A physical implementation needs an equivalent visibility guarantee.

The return path models write traffic, but does not generate numeric MAC values. Routing readout data across channels and buffering/coalescing it are hardware obligations whose additional logic latency is not modeled here. FP16 result width is a design assumption.

Sources: host path; descriptor and completion front end; sequencer and completion conditions.

simFreq is 10¹² ticks/second. The saved clock period is 333 ticks, the simulator's rounded representation of the requested 3 GHz. Some notes divide by 333.33 instead, so their cycle totals differ by roughly 0.1%. The tick ratios and microsecond timings above do not depend on that approximation.

On O3, numCycles excludes quiesced time. Dividing only active cycles gives a false 28.51× matmul speedup. The baseline never sleeps, while the PIM host does.

Use blocks 1/3/5/7 for matmuls and 1–8 for the layer. Each saved file contains 10 blocks; the last two are post-layer bookkeeping and exit, and are excluded.

The machines match within each comparison

Saved config.ini files match in CPU parameters and cache configuration, with the expected workload and PIM-interrupt wiring differences. Both use 16 KiB, 2-way L1I/L1D; a 2 MiB, 8-way L2; and the same four-channel LPDDR5X-8533 PIMony configuration. L1D and L2 have stride prefetchers.

The O3 configuration has a 192-entry ROB, 32-entry load/store queues, and width 8 at fetch/decode/issue/commit. It is a gem5 configuration, not a validated model of a named commercial core.

The baseline uses syscall emulation (SE); PIM uses bare-metal full-system mode (FS). Separate same-code O3 calibration differs by 96 cycles out of approximately 35.58 million, or 0.00027%. That supports a negligible mode effect for that calibration; it does not make the two layer programs identical. On Minor the same calibration differs by 2.7%, and all of it is instruction fetch from a different code layout rather than the mode (section 06).

05 / Inside the layer

The improvement is visible in every projection block.

How the layer is timed

The layer is cut into eight timed sections. After each one the program executes an m5 pseudo-instruction — a word that real hardware would reject and gem5 intercepts — which writes the counters out and zeroes them. The statistics file therefore arrives as eight independent measurements rather than one total, and section N of the source is block N of the file.

#define PHASE() m5_dump_reset_stats()          /* dump the counters, then zero them */

LINEAR(D_WQ, ..); LINEAR(D_WK, ..); LINEAR(D_WV, ..);
PHASE();                                       /* everything above is block 1 */
attention();
PHASE();                                       /* block 2 */

The odd blocks are the matmuls; the even blocks are CPU-only and should be identical on both sides. The markers sit in the same places in both source files, so the blocks line up one to one.

Each matmul block is measured from before the input vector is staged to after the results have been read back and the bias added. Nothing about the offload is left outside the timed region.

Section 08 quantifies it.

“Matmul-only” therefore means complete projection sections, not a timer wrapped around the MAC engines alone.

06 / Why the host matters

A faster host helps the offload path more.

Moving from TimingSimple to O3 reduces the complete PIM layer time by 4.53× and the OpenBLAS layer time by only 2.29×, so PIM's relative advantage grows. But TimingSimple and O3 differ in two ways at once: O3 is pipelined and it executes out of order. gem5's Minor core is pipelined but in order, so it separates the two.

PIM's advantage roughly doubles once the host is a pipelined core. On BERT-base, out-of-order execution adds a further 6–12%. The range is code layout: across three builds of the PIM binary, Minor's time moves by 0.3% and O3's by up to 5.5%.

So the earlier explanation, that O3 wins by overlapping PIM's many independent host memory operations, is wrong as a mechanism. The in-order core already widens the gap: Minor makes PIM 2.34× faster than TimingSimple and the baseline only 1.19× faster. The baseline is memory-bound, with an IPC of 0.21 on Minor and 0.40 on O3, so a better pipeline buys it little. Out-of-order is different: it keeps more DRAM reads in flight, which the GPT-3 comparison below shows matters. PIM's leftover host code is short, latency-bound scalar work that any pipeline speeds up.

Why O3 is given Minor's vector unit

gem5's default Minor has one floating-point and vector unit with a 6-cycle latency. Its default O3 has four vector units with a 1-cycle latency. In the projection sections the baseline is 72% vector instructions and PIM's host code has none, so a default-against-default comparison measures vector width as much as issue order. With one 6-cycle vector unit, O3's baseline slows by 13.4% and PIM by 1.0%, which moves O3 from 15.60× to 17.53×.

The 6–12% is still an upper bound. Minor's single unit also runs scalar floating point at 6 cycles, and about 10% of PIM's host code is scalar floating point; the matched O3 kept its faster floating-point units.

What had to be fixed before Minor could run

Three simulator problems, none of them in the instruction design. The memory model's front end tracked the two channel halves of each read by address, so two reads sharing a half overwrote each other and it reported a read of address 0. The program switched on paging before its page-table stores had landed, which Minor exposes and O3 hides, so the page table is now preloaded in the binary (bert_pim_g7pt). And gem5's Minor has no functional unit for segmented vector loads, so the OpenBLAS baseline stalled silently. With the first fix in place the O3 baseline reproduces to the tick; the rebuilt binary moves default O3 by 1.9%.

How the result was checked
  • Every core executes the same instructions in every block, and the baseline makes the same 226,000 L2 accesses on each.
  • The time asleep waiting for PIM is the same on every core to within 2.5%, about 93,000 cycles per layer, so the device did identical work.
  • Eight sleeps per layer, and identical cache-clean and invalidate counts, on every core and layout.
  • Paging costs nothing inside the timed blocks: one TLB miss and no page walks on Minor.
  • Bare-metal against syscall emulation on Minor differs by 2.7% on identical code. All of it is instruction fetch from a different code layout, not the execution mode.

The two halves of the ratio respond differently to the core. Out-of-order speeds GPT-3's baseline up 2.12× (BERT-base: 1.71×): the baseline streams weights from DRAM, and O3 keeps about 6.8 L2 misses in flight on average against Minor's 1.5. It speeds the PIM run up only 1.71× (BERT-base: 1.81×), because 72% of that run is the host asleep while the device works, and no host core changes that; on BERT-base the share is 46%.

How the GPT-3 result was checked
  • The baseline executes identical instructions in every projection block on every core, and makes the same 3.32 million L2 accesses on each.
  • PIM blocks agree to within 4 instructions. The only asynchronous input in that binary is the completion interrupt: it has no atomics and reads no timers.
  • Sleep is the same on every core within 1.2%, and every core wakes 25 times.
  • The published O3 figure, 19.13×, reproduces exactly from its saved statistics; the rebuilt binary, needed for Minor, gives 19.51× on default O3.
  • All five runs exited normally. Minor's memory parallelism is gem5's default model, not a measured in-order core.

Time quiesced in the completion-wait path

Waiting is now a substantial part of the critical path. The benchmark immediately waits after every job. Scheduling useful independent CPU work during those waits is worth investigating.

Quiesced time is not a direct counter of MAC arithmetic time: it is the portion of the offload/completion interval during which the CPU is asleep. Host activity and device activity can also overlap outside that interval.

An upper bound, not a predicted new speedup

If all 32.29 µs of current waiting disappeared while active host time stayed fixed, the layer would take 45.09 µs: at most 1.72× faster than this PIM run. Real overlap depends on available independent work, data dependencies, and the sequencer's one-active-GEMV limit. This is an optimistic bound, not a measured optimization.

Host optimization also remains relevant: active host time is still 58.27% of the layer. The measurements do not establish that all remaining improvement must come from overlap.

What the fence experiment actually says

The O3 no-fence control takes 74.362 µs versus 77.387 µs with fences: a 3.025 µs difference, or 3.91% of elapsed layer time. The notes' 6.08% used active cycles only. On TimingSimple, the saved elapsed-time difference is 5.99%.

This control removes cache-maintenance instructions while preserving compiler memory clobbers. It is a diagnostic ablation, not a correct replacement for the coherence path. The working decision was to defer a new range-fence instruction; a no-fence comparison does not prove what a real range-fence implementation would save.

Sources: saved O3, TimingSimple, and O3 no-fence statistics. Explanatory context: G8 in GAPS_pim_gemv.md.

Dispatch spends 63.30% of its layer time asleep waiting for completions. Each completion also invokes a handler that scans a 64-slot token mask. The measured net instruction difference is 856,317; repeated host completion handling is the mechanism identified in the analysis.

The two paths deliver different functionality. The dispatch path omits global-buffer fill, READRES, and result writeback/consumption. It schedules the same MAC work, but is not a numerically complete alternative to GEMV. Its 13.87× gap is evidence for the current sequencer/interface design, not a universal bound on every possible dispatch implementation.

Why the measured dispatch schedule is serialized

The working notes report three attempts: 192 commands at once aborted; batches of 32 hung at 2,109 of 2,112 commands; one command followed by a wait completed. A new command to a busy bankgroup can be interpreted as a resume. The sequencer can gate on engine completion; the tested host interface does not expose the same per-engine state.

These failures are documented experiments, not rerun for this report. They describe the tested schedules and implementation, rather than proving that every alternative software schedule must fail.

Attention grows with context length while the projections stay fixed. Row 4 is the control

Residual plus LayerNorm runs on the CPU in both programs and contains no data-dependent branch. It comes out at 1.00×. That is the first direct evidence that the two binaries are equivalent outside the projections — the BERT report had no such check. Any future comparison should verify this row first.

Rows 2 and 6 are why whole-layer comparison is unsound on an out-of-order host. PIMony models timing but computes no values, so the PIM build's activations are essentially just the biases while the baseline's are real numbers. Both exp and tanh have early-return branches, so identical source takes different paths. Measured at 18.1 instructions per exp call across 8,224 calls per layer. The same GELU block on TimingSimple is 0.97×, because that CPU blocks on every memory access and hides the difference. Only the projection rows are branch-free and comparable.

Four differences that had nothing to do with PIM, and were removed

Before these were fixed, the whole-layer figure was contaminated by code differences between the bare-metal PIM build and the hosted baseline:

  • Attention kernel — hand-written C against cblas_sgemv. Both now call the same raw sgemv_t/sgemv_n.
  • Softmax — hand-written k_expf against libm expf. Measured over 164,480 calls: 9.1 against 16.4 cycles per call. The hand-written one is 1.8× faster, so the assumption that it was the slow side was wrong.
  • GELU — hand-written k_tanhf against libm tanhf: 19.39× apart on BERT for code running on the CPU in both builds.
  • Array alignment and code model — matched.

A standing assumption also turned out to be wrong: the bare-metal build was thought to be unable to use OpenBLAS. That is true of cblas_sgemv, which needs the allocator and libc, but the kernels underneath have no undefined symbols at all and link into a freestanding binary. Verified twice — orientation against a scalar reference, and a bare-metal run that only exits if the results are correct.

Three constants that were undersized at the new dimensions

An audit read the layout arithmetic before the first run. The output buffer's size macro had no term for the case where the feed-forward projection itself splits into parts — invisible while the hidden width was 768, but 5,120 elements short at 2,560. It would not have crashed: the overrun lands in alignment padding, which adding the KV cache can close, at which point the device would silently overwrite a live array. The descriptor count and descriptor slot spacing had the same shape of error.

09 / Overlapping the wait

The window can be filled. Filling it is not free.

Section 06 identified waiting as a substantial part of the critical path. At GPT-3 dimensions it is larger still: 71% of the projection sections is the CPU asleep, against 41.8% of the BERT layer.

pim.gemv returns immediately and pim.wait blocks separately, precisely so the host can work in between. Until now nothing used that gap — the program issued a job and waited on the next line.

What makes it possible: one matmul is not one PIM job

A single pim.gemv reduces over at most 1,024 inputs, because a 2 KB DRAM row holds 1,024 FP16 values and a MAC command cannot cross a row. At GPT-3 dimensions a reduction of 2,560 becomes 3 jobs and one of 10,240 becomes 10 — 25 jobs and 25 separate wait windows per layer.

Work may move into a window only if it does not depend on the job being waited on. Block 1 is the one place in the layer where that holds, because Q, K and V are three independent matmuls: reading Q's results needs only Wq.

pim_linear_issue(D_WQ, ...);                        /* Q runs alone   */
pim_linear_overlap(D_WK, ..., D_WQ, bq, Q, ...);    /* read Q under K */
pim_linear_overlap(D_WV, ..., D_WK, bk, K, ...);    /* read K under V */
pim_linear_read (D_WV, bv, V, ...);                 /* no window left */

Wo needs ctx, W1 needs norm1, W2 needs hid — and each is produced by the code immediately before it. The next layer depends on this one's output, so there is no escape upward either. A single inference stream runs out of independent work. Filling the remaining 730,925 cycles requires work from outside the stream — a second request or a second process — which is exactly what the one-job-at-a-time sequencer forbids. The overlap result and the sharing limitation are the same argument from two sides.

Filling the window properly: the score half of attention

Attention splits along the same dependency line. Steps 1–3 — scores, scaling, softmax — need Q and K. Step 4, the weighted sum of the cached values, needs V. PIM produces Q, K and V in that order, so the first three are legal while Wv is still running.

1.  scores  = q_h . Kc_h^T      needs Q and K
2.  scale                        needs nothing new
3.  softmax                      needs nothing new
4.  ctx     = weights . Vc_h     needs V

That is roughly a million cycles of work against 214,403 of sleep. Unlike the read-back, there is far more than enough.

Note on the metric: the scores move out of block 2 and into block 1, so “matmul-only” stops being a clean category for this build. The comparison is blocks 1+2 together — the same work either way, with only the boundary between them moved.

Why this is the result, and not a failure

The thesis this work belongs to opens on a single sentence: PIM operations coexist with ordinary host memory accesses.

Until this run they never did. The host slept through every PIM job, so there was nothing to interfere with. This is the first time the CPU streams the key-value cache — 5.02 MiB, against a 2 MiB L2 — out of DRAM while the PIM engines are computing inside it. The measurement is what that costs: 4.7% on every host memory access.

So the idle window is not spare capacity waiting to be used. Occupying it consumes memory bandwidth, and here the cost exceeded the gain. That is a more useful thing to report than a ratio, because it names the resource the host is actually contending for.

One limit to state. This shows the contention is in the memory system. It does not separate PIM's commands competing with the CPU from the CPU's own access pattern becoming more fragmented by being interleaved with descriptor writes and fences. Both are interference.

Splitting it: give the PIM priority instead

The device's scheduler can favour the CPU, which is the default (a CPU read may interrupt a MAC), or the PIM (CPU reads and writes wait while that bankgroup has PIM work queued). If the penalty is PIM competing with the CPU, it should grow when the PIM gets priority. A first attempt failed because the device's alternative configuration files also change the compute mode; this run changes the policy line and nothing else.

The penalty moves with the policy, by about 2 points. So part of it is PIM's commands competing with the CPU's. Instruction counts and miss counts match across the two policies.

The control is the no-overlap build because the overlap build cannot finish under PIM-first (below). Against that build the CPU-first penalty is 6.5% rather than 4.7%; the difference, 1.8 points, comes from the overlap structure itself.

What it cannot split. Even with CPU priority, a CPU read that interrupts a MAC still pays to close the PIM's DRAM row and open its own. No policy removes that cost, so the 6.5% under CPU-first is not purely the CPU's access pattern. The experiment bounds the policy-sensitive part, about 2 points, not the whole.

Under PIM-first, one run never finishes: a bug in the memory model

The overlap build ran about 3½ hours without reaching its first measurement point. Its command trace is nothing but row openings and closings on one DRAM bank. The sequencer's vector load and a CPU read want different rows of that bank, and each closes the other's row one cycle after it opens. A read needs 19 cycles after its row opens, so neither ever gets one.

Real DRAM cannot do this: a row must stay open 45 cycles before it can be closed. The model skips that check because it times the close by the subarray of the request asking for it, not of the row being closed, and the two rows sit in neighbouring subarrays. The fault is in the memory model, not in the instructions or the sequencer. The other two PIM-first runs completed normally.

Open: PIM-first also made the PIM jobs slower

With no overlap and the host asleep during every job, the time spent waiting for PIM grew 20.6% under PIM-first, with identical instructions. Giving the PIM priority made the PIM slower. One suspected cause, not yet traced: the sequencer writes its results back as ordinary writes, which PIM-first holds back while that bankgroup has PIM work queued, including the sequencer's own MACs.

A wrong result, and what caused it

The first attempt reported the overlap as a net loss — 19.13× falling to 18.37× — with 28.9% of the sleep reclaimed. Both halves were artefacts of the control.

Consuming one slab at a time required rewriting the read-back so that it made a pass over the output array per slab, rather than one pass over outputs with the running sum held in a register. For the feed-forward reduction that is 25,600 stores instead of 2,560. It cost 23% more instructions and had nothing to do with overlap. The control carried the same penalty, so the comparison between the two builds was valid while the absolute number was not.

The repair is confirmed by measurement: the restored control gives 1,345,853 cycles against the original's 1,349,774, a difference of 0.29%.

The rule it establishes: a control must differ from the test build by one compile-time flag and nothing else — not by being an earlier run of roughly the same thing. This is the second time an unrelated code change contaminated a comparison in this work; the first was the C library's exp and tanh against the hand-written versions, in section 08.

The experiment became more complete.

The older numbers describe different binaries, regions, and CPU models. Reading them as one continuous performance curve would be misleading.

5.70× · Original whole-layer result

Both binaries lacked hardware FP16 conversion support in their build flags. Software conversion routines inflated host work. The output path was also incomplete. This result is superseded.

11.42× → 10.64× · Intermediate whole-layer runs

Adding zfh removed software FP16 conversions. Cleaning the operand vector then charged the necessary cache-to-DRAM handoff. These were still incomplete result-consumption experiments.

9.55× · Earlier layout-adjusted whole-layer estimate

Instruction placement affected TimingSimple's fetch costs. Later analysis also found the two alignment flags did not provide independent layouts. Treat this as historical analysis, not the current endpoint.

8.43× matmul / 7.21× layer · Complete TimingSimple path

The host now loads the output buffer, invalidates stale cache lines, converts FP16 results, and sums W2's three partials. READRES over-issue is corrected. More of the required work is being measured.

15.30× matmul / 13.95× layer · O3, BERT-base

The complete offload runs on an out-of-order host. First reported as 15.28× / 14.72× against a baseline that used the C library's exp and tanh where the PIM build used its own; re-measured 24 September with that difference removed. The projection figure moved 0.13%; the layer figure moved 5.2%.

19.13× matmul / 7.84× layer · O3, GPT3-2.7B decode

The workload itself was corrected: BERT-base at sequence length 1 is not a configuration BERT has, and the access pattern was GPT decode all along. Larger projections suit the device better. The layer figure falls because CPU-side attention now dominates — see sections 08 and 09.

16.54× Minor / 17.53× O3 · in-order against out-of-order, BERT-base

The first in-order pipelined host. Minor needed three simulator fixes and a rebuilt PIM binary with its page table preloaded; on that binary default O3 moves from 15.30× to 15.60×. The same comparison on the GPT-3 layer, with the page-table fix ported to its PIM binary. The order flips: out-of-order speeds the streaming baseline up more than the mostly-waiting PIM run. The host comparison is reported per workload from here on.

A lower ratio after adding missing work is a better experiment. The result becomes more defensible when both the outgoing and returning sides of offload are charged.

  • 8,448 READRES commands: the old sequencer issued four readouts where the command format permits one per bankgroup. Correct derived count: 2,112. There are still 8,448 scalar partial-result elements.

Why the command-count evidence is labeled separately

The available bert_pim_g7/dramsim3_final.txt contains zero PIM command counters. Phase-level statistics resets clear PIMony's counters, so that exit snapshot does not preserve a full-layer count. The selected O3 run has no archived full-layer DRAM counter file.

The original bert_pim_v3 archive does preserve 110,592 COMP steps and 32 GWRITEs, but also the historical, incorrect 8,448 READRES count. Therefore, this report does not claim to have reverified a corrected 2,112 READRES total from a current raw counter archive. That total is derived from source and recorded as measured in the working notes.

A future counter-validation run needs a preserved full-layer counter interval. Save DRAMsim3 output immediately: it is written at exit to the gem5 root and can be overwritten by the next run.

The scope of the conclusion

  • One layer, one vector. This is not a full BERT-model latency, accuracy, throughput, energy, or large-batch result.
  • Two host cores, both workloads. Minor (in order) and O3 (out of order) are gem5 configurations, not models of named commercial cores, and which one shows the larger speedup differs between BERT-base and GPT3-2.7B. The speedup is not an ISA constant; host parameters, memory system, and code layout matter.
  • One active GEMV at a time. Overlap and multi-process scheduling are not established by these layer runs.
  • Timing model assumptions. FP16 result width, posted-write visibility, and uncharged result-routing logic need to remain explicit.
  • Measurement precision. gem5 is deterministic: rerunning a binary reproduces its ticks exactly. The uncertainty is code layout. A three-build sweep moved Minor's PIM time by 0.3% and matched O3's by up to 5.5%, which is why the out-of-order gain is reported as 6–12%. The notes report about ±3% layout sensitivity for TimingSimple. None of this is a statistical confidence interval.

12 / What to report

Lead with the complete projection result.

In a gem5/PIMony timing simulation of one GPT3-2.7B decode layer at batch 1, pim.gemv reduced the elapsed time of the six FP16 linear-projection sections from 8,607.89 µs to 449.93 µs on the configured O3 host, a 19.13× speedup over a tuned OpenBLAS baseline running the same kernels. At BERT-base dimensions the same measurement gives 15.30×. The measured sections include operand preparation, cache maintenance, completion waiting, and host result consumption.

Add the qualification directly after that claim: PIMony models execution timing and traffic, not numerical GEMV results.

Do not quote a whole-layer ratio on an out-of-order host. Because the device produces no values, branchy CPU code downstream of a projection takes different paths in the two builds — measured at 18.1 instructions per exp call. The projection sections contain no such branches, which is what makes them the quotable region. Section 08 has the evidence and the 1.00× control that demonstrates the rest of the two binaries now match.

On overlap, report the interference, not a speedup. Part of it is PIM/CPU contention: giving the PIM scheduling priority raises the penalty by about 2 points.

Putting host work inside the device's compute window does fill it — 71,772 cycles of waiting absorbed, at identical instruction counts. But the same work then costs 4.7% more on every memory access, because the CPU and the PIM engines are using DRAM at the same time for the first time. The idle window is not spare capacity. That measurement is what the opening claim of this project — that PIM operations coexist with ordinary host memory accesses — actually costs, and it had never been exercised before, because the host had always been asleep. Section 09 has the evidence.

On the host, compare cores that have the same vector unit, and name the workload. PIM's advantage roughly doubles once the host is a pipelined core, from 8.43× on TimingSimple to 16.54× on in-order Minor for BERT-base, and out-of-order execution adds a further 6–12% there (17.53× on O3). On GPT3-2.7B the order flips: 28.29× on Minor, 22.81× on O3. TimingSimple is a first pass only: it stops on every memory access and understates the offload about twofold. Section 06 has the evidence.

What the architecture result says

The sequencer turns a small number of shaped submissions into the memory-side command schedule, while managing readout and completion. Against the tested serialized dispatch path, that cuts waited completions from 2,112 to 8 and projection-section elapsed time by 13.87×. The different functionality of the dispatch path must accompany that comparison.
