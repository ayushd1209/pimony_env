1 · The main result

PIM runs the matrix multiplies 12–28× faster than the best CPU code

Why it matters. At batch 1 the matrix–vector multiplies are limited by how fast DRAM can deliver the weights. pim.gemv does the multiply inside the DRAM, so the weights never travel to the CPU.

  • The baseline is OpenBLAS, vectorised, on the same simulated machine. Only the matmul sections are compared (stats blocks 1, 3, 5 and 7).
  • The speedup depends on the CPU. The PIM run contains a fixed wait while the PIM works, about 950k cycles on GPT-3, the same on Minor and O3. A faster core shrinks the CPU-only run 2.5× but the PIM run only 1.4×, so the ratio falls.
  • A bigger ratio is not a faster machine. O3 + PIM finishes first on both workloads (GPT-3: 1,589,781 against 2,290,759 cycles on Minor + PIM).
  • The headline pair is default O3 vs default Minor. The two cores also differ in vector hardware (O3: 4 units, latency 1; Minor: 1 unit, latency 6); the last column removes that difference.

2 · The workload

Each projection becomes one or more PIM jobs

One PIM dot product covers at most 1,024 inputs, the FP16 contents of one 2 KB DRAM row, so a longer reduction is split into several jobs. Attention, GELU, residuals and LayerNorm stay on the CPU.

BERT-base layer, 1 tokenMatrix (outputs × inputs)pim.gemv jobsSteps per dot
Q, K, V3 × (768 × 768)348

Total7,077,888 weights816 FP16 per step

GPT3-2.7B decode uses the same mechanism on wider matrices: 25 jobs per layer, because its 2,560- and 10,240-long reductions split into 3 and 10 slabs.

3 · One instruction vs many

One pim.gemv beats per-command pim.dispatch by 1.30×, and cannot crash the PIM

Why it matters. Every hand-off from CPU to PIM costs a command and a completion. The question is whether one coarse instruction per matrix–vector multiply is better than one fine instruction per MAC command.

BERT layer, default O3, same 2,112 MAC commandsMatmul cyclespim.gemv faster by
pim.gemv (8 instructions)256,300–
pim.dispatch, 32 at a time, then wait333,4551.30×
pim.dispatch, 1 at a time, then wait2,934,99211.45×
pim.dispatch, all 192 at oncePIMony aborts after 49 commands
  • Quote 1.30×. 32 at a time is the fastest pim.dispatch schedule that runs: each batch puts exactly one command on each of the 32 engines.
  • pim.dispatch also does less. It never loads the input vector into the PIM and never reads the results back, because no instruction exists for those steps, so its answer is never usable.
  • pim.dispatch can crash the PIM. Its completion only reports the last command of a batch, so the program has to know how many engines there are. Sending all 192 put a second command on an engine 190 cycles into its 192-cycle multiply, and PIMony aborted. The pim.gemv sequencer sends a command only when that engine is free.

4 · CPU work during the PIM's wait

Filling the wait helps a little, and sharing the memory costs about 5%

Why it matters. While the PIM works, the CPU sleeps. Giving it useful work in that time shortens the run, but then the CPU and the PIM use the same DRAM at the same time.

GPT-3 decode, default O3Block-1 sleepTicks per L2 miss, blocks 1+2
CPU only sleeps during each job234,07675,296
+ reads results back during the next job189,02276,653
+ attention scores during the wait132,30679,110
  • Overlap works, but the prize is small. Reading results back during the next job fills 45,054 cycles of sleep. 79% of all sleep sits in matmuls that need the step right before them, so a single inference stream has nothing to put there.
  • Sharing the memory costs +5.1% per CPU memory access (first row to last row). With PIMony set to give the PIM priority it is +8.7%, so part of the cost is the CPU and the PIM competing for the banks.
  • Attention in the wait does not pay. It fills 56,716 cycles of sleep but makes the CPU's own work 93,556 cycles slower, so blocks 1 and 2 end 36,840 cycles slower.

Open. Giving the PIM priority also makes the PIM's own jobs slower: +19.8% on GPT-3, +12.5% on BERT. The cause is unknown. The sequencer's result write-backs were tested and ruled out.

5 · Where PIM's case ends

Processing many tokens at once takes away PIM's advantage

Why it matters. PIM wins when the CPU waits for weights. With many tokens at once, every weight fetched is used once per token, so the CPU waits far less per multiply. This run is CPU only: a BERT layer through OpenBLAS on O3.

  • Math per byte read rises 71× from 1 to 128 tokens and peaks at 256 (89×). PIM's case is strongest at 1 token, which is GPT-3 decode, and gone by 64 tokens.
  • BERT in real use runs at 128 to 512 tokens, the case least favourable to PIM: 18 to 22 multiply-adds per byte, about 1.1 to 1.3 GB/s read, and the highest IPC of the sweep. The BERT rows in section 1 are a BERT-sized layer at 1 token, not BERT inference.
  • Past 256 tokens the intensity falls back, because the activations stop fitting in the 2 MiB L2. Data written back to DRAM, which can only be activations, grows 8× from 128 to 512 tokens for 4× the tokens; the faster-than-linear part is attention's score table. This baseline stores the whole table, as unfused attention does.

6 · Validation

The offload does the right work on every CPU

  • The right commands reach the PIM. One BERT layer sends 2,112 MAC and 2,112 readout commands, and the CPU sleeps exactly 8 times, once per pim.gemv. The 110,592 MAC steps equal 7,077,888 weights ÷ 64 per step.
  • The instructions behave the same on every CPU. 9 tests on TimingSimple, Minor and O3 all finish, and for each test the PIM receives the identical list of commands from all three CPUs.
  • pim.fence.inv invalidates on O3. The reload after the fence now goes to DRAM on all three CPUs (2 accesses to the line, 3 for .flush). Before the fix, O3 read the stale cached copy (1 and 2).

7 · Known limits

What these numbers do not cover

  • PIMony computes no values. Only the matmul sections are comparable; CPU code that branches on their results diverges, so whole-layer ratios are unsound on pipelined CPUs.
  • One layer, batch 1. Section 5 shows why batch 1 is the case that matters for PIM.
  • The result width is our assumption: FP16, 2 bytes per result. The PIMony paper does not give one.
  • Fences cost 22.7% of BERT's PIM matmul time on O3. That is the most a range fence could save; the design is parked.
  • One pim.gemv at a time. There is no sharing between processes yet.
