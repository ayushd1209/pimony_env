Is the CPU Baseline Fair?

A walk-through, from first principles. Every concept is introduced before it's used, so this can be read cold.

Part 1 — The question

The thesis will end with a sentence like “PIM is N times faster than a CPU.”

That only means something if the CPU was doing its best. Race a car with the handbrake on and winning proves nothing about your engine. So if the baseline kernel is slow for a fixable reason, N is inflated by an unknown amount — and that is the first thing a reviewer attacks.

Hence: is the CPU baseline fair? Everything below exists to answer that one question.

Part 2 — Nine concepts

Concept 1

gem5 is a simulator, not a chip

There is no hardware here. gem5 is a program that pretends to be a computer, instruction by instruction, and counts what would have happened.

That's why we can ask things no real machine could answer — like “how many prefetches turned out useful.” And why runs take minutes: simulating one second of a CPU takes hours of real time.

The file configs/pimony/se_bert.py is the blueprint. It describes a machine in Python, and gem5 builds it.

Keep: every number here comes from a described machine. Change the description, change the numbers.

Concept 2

Cycles are the unit of time. IPC is how busy you were.

The machine runs at 3 GHz — three billion ticks per second. One tick is a cycle, and everything takes some whole number of them. Cycles are the only currency that matters.

Two numbers come out of every run:

simInsts    = how many instructions ran     (the work)
numCycles   = how many ticks it took        (the time)

Divide them and you get IPC — instructions per cycle. This machine can start 8 instructions per cycle, so 8.0 is the ceiling and never reached. IPC of 0.2 means the machine was mostly idle. IPC of 1.5 means it was working.

Keep: low IPC is a symptom of stalling. It tells you to go find out what the machine was waiting for.

Concept 3

Memory is a ladder, and the rungs are far apart

Data can live in three places, and they differ enormously in speed:

   CPU
    |    ~2 cycles
  L1D   16 KiB      tiny, very fast
    |    ~20 cycles
   L2    2 MiB      small, medium
    |    ~300 cycles
  DRAM   2 GB       huge, very slow

L1 is roughly 150× faster than DRAM. The whole ladder exists for that one reason.

Data moves in 64-byte blocks called cache lines — 16 floats at a time, never one. A miss means a level didn't have what you asked for and had to go down a rung. So “53% L1D miss rate” means: half the time, the fast path failed.

Keep: miss rate isn't a curiosity. It's a multiplier on runtime, because each miss costs a trip down the ladder.

Concept 4

The workload: one BERT layer

BERT is a language model. One layer of it is what we measure — the real model stacks twelve.

Almost all the arithmetic is in one function, linear(), which computes every output as a weighted sum of every input. With 3 inputs and 2 outputs:

y0 = b0 + w00·in0 + w01·in1 + w02·in2     3 multiply-adds
y1 = b1 + w10·in0 + w11·in1 + w12·in2     3 multiply-adds

So the work is n_out × n_in multiply-adds. In BERT-base those are 768 or 3072, and bert_layer() calls linear() six times:

Wq  768 -> 768      589,824
Wk  768 -> 768      589,824
Wv  768 -> 768      589,824
Wo  768 -> 768      589,824
W1  768 -> 3072   2,359,296
W2  3072 -> 768   2,359,296
                  ---------
                  7,077,888  multiply-adds per token

The weights are 28.3 MB of fp32 numbers. Compare that to the 2 MiB L2: the weights are 14× too big to fit. So every weight must come from DRAM. That's not a flaw in the code — it's the shape of the problem.

Keep: 7,077,888 multiply-adds and 28.3 MB of weights, per token. Both recomputable on paper from the source.

Concept 5

SEQ — how many tokens at once

SEQ is how many words are pushed through together. The crucial asymmetry:

arithmetic   grows with SEQ    (each weight used SEQ times)
weight size  does NOT grow     (Wq is 768x768 either way)

That's weight reuse, and it's the entire reason batching can help.

SEQ=1 is decode-shaped — one word at a time, each weight used once, no reuse at all. Real BERT runs at 128 or 512.

Keep: raising SEQ adds arithmetic almost for free in memory terms. Whether that helps depends on Concept 9.

Concept 6

Kernel, library, and “tuned” versus “reference”

A kernel here means the small inner function that does the maths. Not an OS kernel. linear() is a kernel.

A library is precompiled code you link in. OpenBLAS is the standard one for linear algebra.

And every serious library ships two versions of each kernel:

reference:  plain readable C. Correct, portable, slow.
tuned:      hand-written for one machine's vector instructions.

OpenBLAS's reference GEMV is 68 lines of ordinary C. Its tuned version is 133 lines of vector intrinsics, and the tuned GEMM kernel compiles to 3,901 vector instructions.

Keep: “we compared against OpenBLAS” means nothing without saying which target. Its RISCV64_GENERIC is documented as the scalar reference path.

Concept 7

A dependency chain can't be sped up by more hardware

Two operations. Sometimes the second must wait:

a = 2 + 3        
b = a x 10       needs a  -> must wait

a = 2 + 3
b = 7 x 10       doesn't need a -> can run at the same time

Draw an arrow when one needs another, and you have a dataflow graph. A line of operations each waiting on the last is a dependency chain.

Now the inner loop of linear():

s = s + w[0]*v[0]
s = s + w[1]*v[1]
s = s + w[2]*v[2]

s --> s --> s --> s --> ...    7,077,888 links long

Each step needs the previous total. In machine code it's one register: fmadd.s fa5,fa3,fa4,fa5 — destination fa5 also appearing as an input.

This machine has two floating-point multiply units, each taking 5 cycles and able to accept a new job every cycle. So it can hold 10 multiply-adds in flight. A chain offers it one. The units sit unused 9 opportunities out of 10 — not because they're slow, but because nothing else is ready.

And out-of-order execution can't rescue it. Renaming fixes false dependencies (two unrelated things reusing one register name). This one is real: the sum genuinely needs the previous sum, and no hardware can use a value that hasn't been computed.

Keep: the fix is restructuring, not more hardware. Eight running totals instead of one gives eight independent chains, each an eighth as long — and eight ready jobs instead of one.

Concept 8

The cycle budget — how to find a bottleneck

This is the method behind every conclusion here, and it's four steps:

1. guess where the time went
2. compute what that guess predicts, in cycles
3. compare to measured
4. if it explains ~95%, stop. if 20%, guess again.

A CPU can only ever wait on three things: dependencies, memory, or the front end. So the search space is tiny.

Worked example. Scalar run, hypothesis “it's the dependency chain”:

7,077,888 multiply-adds x 5 cycles = 35.4M cycles predicted
                                     37.3M cycles measured
                                     -> 95% explained
Keep: the budget tells you which of 1,500 statistics to read. Without it you're browsing. This is why no cache statistic was ever examined for the scalar run.

Concept 9

Arithmetic intensity — and why PIM cares

One number decides whether memory or compute is your limit:

arithmetic intensity = multiply-adds / bytes fetched from DRAM

Low intensity — lots of bytes, little maths — means the machine spends its life waiting for data. Memory-bound.

High intensity — much maths per byte — means the machine is busy computing and fetches hide behind the work. Compute-bound.

This is the crux of the whole project. Processing-in-memory only helps a memory-bound workload. Moving compute next to the DRAM banks is pointless if the CPU wasn't waiting on DRAM in the first place.

Keep: so the question “does PIM help?” becomes the measurable question “what is this workload's arithmetic intensity?” That is what Part 4 measures.

Part 3 — The seven experiments

Each was forced by the answer to the one before. The chain is the argument; the numbers alone aren't.

  1. A — Is my hand-written loop worse than a real library?

    Built OpenBLAS, swapped it in. 37,304,666 vs 37,303,109 cycles — identical.
    Means nothing yet. We'd built the RISCV64_GENERIC target — the reference kernels from Concept 6. Its GEMV is the same single-accumulator loop. Two naive kernels compared to each other.

  2. B — Slow from too much work, or from waiting?

    -funroll-loops deleted 18.5M instructions (43%) and runtime moved 1%. IPC fell 1.155 → 0.664.
    Means waiting (Concept 7). Deleting nearly half the work bought nothing, so instruction count was never the limit. The cycle budget then confirmed it: 95% explained by the chain.

  3. C — What does a properly tuned kernel buy?

    Rebuilt OpenBLAS as RISCV64_ZVL256B with GCC 16, verified vectorized by disassembly (22,401 vector instructions). 4,779,345 cycles — 7.8× the original, and 1.56× better than our own auto-vectorized loop.
    Means the baseline was not fair. There was 1.56× on the table even against compiler-vectorized code.

  4. D — Is the prefetcher wasting bandwidth? It reported 4.3% accuracy.

    Removed both prefetchers. Things got 8.1× slower for our own kernel and 1.84× for the library's.
    Means the metric lied. Its “accuracy” counts only prefetches still in L1 when needed — but a 16 KiB L1 streaming 28 MB evicts them at once, while they still land in L2 and save the DRAM trip. A statistic measures a definition, not value. Only an A/B run measures value.

  5. E — Route every matmul through the library

    New bert_blas.c: attention's two matmuls become GEMM calls too. 4,729,365 vs 4,779,345 — 1% apart.
    A validation, not a result. At SEQ=1 attention is a rounding error. But note the signature: 3.2% fewer instructions bought 1.0% fewer cycles — Concept 8 confirming itself from a second angle.

  6. F — A gem5 bug, found and fixed

    SEQ=16 segfaulted inside gem5. gdb showed it requesting vector register 41 from a 40-entry set. gem5 stages split vector instructions in 8 private scratch registers but computes how many it needs from a runtime value — nothing reconciles them. Fixed by raising the pool to 64.
    Verified transparent: re-running SEQ=1 gave bit-identical numbers. Every earlier result stands.

  7. G — The cache was too small, and it was distorting everything

    At SEQ=128 the machine pulled 247.9 MB from DRAM for a ~34 MB footprint. Cause: GEMM copies blocks into re-laid-out buffers, and those buffers must stay in cache to pay off. At 256 KiB they didn't, so they were re-fetched endlessly. Raising L2 to 2 MiB cut traffic to 52.3 MB — 4.7× less.
    Means the earlier traffic numbers were a config artifact, not a property of the workload. The whole sweep was re-run at 2 MiB.

Reading it

  • Up to 128 the DRAM column barely moves. 28.4 → 52.3 MB while the work grows 128×. That's weight reuse (Concept 5) working exactly as intended — and it was completely hidden by the cache artifact from experiment G.
  • Past 128 it grows faster than the work (86 → 227 MB): the activations stop fitting in the 2 MiB L2. Data written back to DRAM, which can only be activations, grows 8× from SEQ=128 to 512 (17.8 → 142.7 MB) for 4× the tokens; the faster-than-linear part is attention’s score table, which grows as SEQ². This baseline stores the whole table, as unfused attention does.
  • Batching is worth 6.0× per token at its best, SEQ=256 (5,588,703 → 932,491 cycles). Past that the per-token cost rises again, to 1,039,491 at 512, as attention’s SEQ² work and traffic grow.
  • Small batches lose. SEQ=4 costs more per token than SEQ=1. GEMM's block-copying setup needs roughly 16 tokens before it pays for itself.
  • The machine gets far busier. IPC 0.224 → 1.827, L1D misses 53.2% → 11.4% from SEQ=1 to 512. It stops waiting and starts computing.
  • Bandwidth pressure collapses: 15.28 → 1.19 GB/s, from 11% of the ~136 GB/s available down to 0.9%, and stays there: 1.08–1.28 GB/s from SEQ=128 to 512, under 1%.

The same shift in cycle-budget terms

Apply Concept 8 at both ends. The arithmetic floor is multiply-adds ÷ 8 vector lanes ÷ 2 FP units:

SEQ=1     442K of   5.59M cycles  ->   8% is arithmetic
SEQ=128  58.2M of 131.54M cycles  ->  44% is arithmetic

At one token the machine is overwhelmingly waiting. At 128 it is nearly half busy computing. Same code, same machine — only the batch size changed.

Part 5 — What it means for PIM

From Concept 9: PIM helps a memory-bound workload and does nothing for a compute-bound one. So the curve above is a direct measurement of where PIM can help.

Finding 1 — the baseline was not fair, and now it is

A tuned library kernel is 7.8× faster than the original loop and 1.56× faster than our own vectorized version. Any PIM speedup measured against the old baseline was inflated. The new baseline is a citable library build, verified vectorized by disassembly — a much stronger position than “a loop I wrote.”

Finding 2 — at SEQ=1 the CPU cannot use the bandwidth it has

The best kernel reaches 15.3 GB/s of roughly 136 GB/s — 11%. Arithmetic explains only 8% of its cycles; the rest is waiting. And reaching even 11% needs a speculative prefetcher — without one it drops further.

This is a sharper argument than any speedup ratio. The limit is not DRAM speed. It is that the CPU structurally cannot keep enough requests outstanding to use what is already there. Compute sitting next to the banks has none of those constraints.

Finding 3 — and batching takes that argument away

Arithmetic intensity rises 71× from SEQ=1 to SEQ=128 (0.25 → 17.79 MACs/byte), peaks at SEQ=256 (22.22) and is back at 17.74 by 512. Bandwidth pressure falls from 11% of peak to under 1% and stays there across BERT’s real range of 128–512 tokens.

So PIM's case exists at SEQ=1 and is essentially gone by SEQ=64. That is a real constraint on the thesis framing, and it agrees with the literature targeting memory-bound decode rather than batched prefill — except this is measured in-house rather than cited.

Still weak — say these before someone else does

  • The softmax is hand-written and grows as SEQ². It makes HEADS × SEQ² calls to expf — negligible at SEQ=1, roughly 13% of instructions at 128. Defensible (PyTorch also uses custom kernels there) but ours is naive.
  • One layer, not twelve. Results are per-layer. State it explicitly.
  • fp32 only. Real inference uses int8 or fp16, halving or quartering bytes moved — which directly changes the intensity numbers Finding 3 rests on.
  • Past SEQ=256 the curve is shaped by this baseline’s attention. It stores the whole score table, as unfused attention does, so the table’s SEQ² traffic pulls intensity back down at 384 and 512, and instructions per token rise 22% from 128 to 512. A fused attention kernel would avoid most of that. The PIM conclusion does not depend on it: the CPU stays far from memory-bound at every length.
  • The L2 size is now a documented choice, not a default. 2 MiB, matched across se_bert.py and fs_bert.py. Any PIM performance number taken at the old 256 KiB needs re-running.
  • Don't compare SEQ=1 across L2 sizes. The bigger L2 holds dirty lines longer, so writebacks that used to happen during setup land inside the measured region — 4,518 → 32,916 of them. That's a region-boundary effect, not the cache being worse.
  • RESULTS_gemv.md is superseded (removed 4 Oct; in git history). Its 6.1× vector speedup, 7.9× cache-tuning figure and “not memory-bandwidth-bound” conclusion were all measured on the unfair baseline. Its millisecond column also assumes 1 GHz while the config runs at 3 GHz.
  • The gem5 fix is local. Not upstreamed, and it raises a constant rather than fixing the underlying mismatch.

Two habits worth more than the results

1 — account for your cycles before changing anything

Concept 8. Guess, predict in cycles, compare. ~95% match means stop looking. This is what makes “it's memory-bound” an argument rather than a vibe — and a reviewer will ask what fraction of cycles the misses actually explain.

2 — remove something and remeasure

If you delete a large fraction of X and the runtime doesn't move, X was not your bottleneck. One run, no theory needed. Experiment B settled a question in a single run that no amount of reasoning from statistics would have. Experiment D is the counterexample: reasoning from a statistic gave exactly the wrong answer until an A/B run corrected it.

Glossary

arithmetic intensity
Multiply-adds per byte fetched from DRAM. Low = memory-bound, high = compute-bound.
cache line
The 64-byte block memory moves in. You never fetch one float.
compute-bound
Limited by how fast arithmetic can be done. PIM does not help.
cycle
One tick of the clock. At 3 GHz, a third of a nanosecond.
dependency chain
Operations each needing the previous one's result. Cannot be sped up by adding hardware.
GEMM / GEMV
General matrix-matrix / matrix-vector multiply. SEQ=1 uses GEMV, SEQ>1 uses GEMM.
IPC
Instructions per cycle. How busy the machine was; 8.0 is this machine's ceiling.
kernel
The small inner function doing the maths. Not an OS kernel.
LMUL
How many vector registers RVV gangs together as one.
memory-bound
Limited by waiting for data. The regime where PIM has a case.
miss rate
Fraction of accesses a cache level couldn't serve, forcing a trip down the ladder.
MSHR
Miss-status holding register. Tracks one outstanding miss; you have 16, capping how many can be in flight.
packing
GEMM copying matrix blocks into re-laid-out buffers. Pays off only if the buffers stay in cache.
prefetcher
Hardware guessing what you'll need next and fetching early.
reference kernel
A library's plain-C version. Correct and portable, not fast.
register renaming
Hardware giving each write its own physical storage, so reused register names stop looking like real dependencies.
ROI
Region of interest. The part of the program the statistics cover — here, one bert_layer() call.
RVV
The RISC-V Vector extension. One instruction operates on several numbers at once.
SEQ
Tokens processed together. Weight reuse rises with it; weight size does not.
tuned kernel
Hand-written for one machine's vector instructions. What you must compare against.
VLEN
Vector register width in bits. 256 here, so 8 floats per instruction.
