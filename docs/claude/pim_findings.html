The gap being closed

Why the host needs new instructions

DRAM-PIM moves computation into the memory device, and recent designs run it asynchronously and preemptively alongside ordinary host accesses. But the host side has no language for it: RISC-V offers no way to dispatch asynchronous PIM work, no fence to order CPU accesses against in-flight PIM computation, and no mechanism to observe completion.

Existing prototypes paper over this with memory-mapped I/O and ad-hoc driver conventions — which neither compilers nor microarchitectures can reason about for correctness or ordering. The thesis replaces that with ISA-level primitives that carry their own analyzable semantics, plus the microarchitectural mechanisms to honor them.

The extension

Three instructions, one custom opcode

All three live under the custom-0 opcode (0x0B), selected by funct3. Each carries its intent in the instruction itself, so the toolchain and the pipeline can reason about it.

pim.dispatch async · non-blocking

Hand memory-side work to the PIM engine and return immediately with a tracking token.

pim.dispatch rd, rs1, rs2  —  funct3=0x3 · bit25=completion · rd=token · rs1=DRAM addr · rs2=num_macs (column-step count)
  • Issues as a single read-shaped bus transaction carrying a packed descriptor (token · asid · completion · num_macs) in a side-band field — not a data write. The PIM device intercepts it on a flag, launches the MAC engine, and acknowledges without touching DRAM.
  • The completion bit (encoding bit 25) states whether this MAC closes its batch. Set: the device reports completion and a token is minted. Clear: the MAC runs and is charged timing, but raises no completion event and mints no token. A batch is therefore N−1 silent dispatches followed by one that reports. The bit names an architectural fact — the batch boundary — deliberately not the delivery mechanism, so interrupt-vs-poll delivery remains a free variable.
  • The token is minted on the core and written to rd at issue — nothing is fetched back, so the core never stalls on the dispatch.
  • Read-mode address translation means read-only operand pages don't fault — a prerequisite for sharing weight matrices across address spaces.
  • Flagged STRICT_ORDER (strongly-ordered device memory) so the dispatch is issued non-speculatively — it never fires down a mispredicted path.
pim.fence ordering

Order the CPU access path against the in-flight PIM compute path.

pim.fence.cl / .inv / .flush  —  funct3=0x1 / 0x2 / 0x4 · reuses the Zicbom cache-maintenance datapath
  • Clean before dispatch (.cl): write a dirty operand line back to DRAM so the PIM engine reads fresh data — closes the pre-dispatch write-after-read hazard.
  • Invalidate after completion (.inv): drop a stale cached copy so the host re-reads the PIM result — closes the post-completion read-after-write hazard.
  • This is single-core device coherence (core ↔ memory-side engine), not multi-core protocol coherence — the same discipline as DC CVAC/DC IVAC around a DMA engine. It reuses gem5's faithful cache-maintenance mechanism.
pim.wait completion

Block until a specific dispatched PIM operation reports done.

pim.wait rd, rs1, imm  —  funct3=0x0 · rs1=token · wfi-class hint · interrupt-driven completion
  • Waits on the token returned by pim.dispatch, using a per-token scoreboard so completions can be observed out of order.
  • Completion is delivered as a faithful full-system interrupt plus an MMIO done-register — replacing the "teleport" shortcut used earlier.
  • Defined as a wfi-class hint: it inherits RISC-V wait-for-interrupt semantics — may complete spuriously, sleeps only while no enabled interrupt is pending — and narrows the wake condition from "any interrupt" to "my token" by re-executing until its own completion is observed. Being a hint is the safety property: a lost completion stalls the program, never the machine, because the hart stays interruptible throughout.
  • Verified on all three host models, including out-of-order — see the O3 finding below for the two mechanisms that make delivery possible there.

What we learned

Key design findings

Dispatch is a command, carried by the instruction — not a driver convention

The dispatch is a read-shaped transaction with a side-band descriptor and a core-minted token. Because the semantics live in the instruction, a compiler sees "asynchronous PIM dispatch, non-speculative, ordered" rather than an opaque store to a magic address. That analyzability is precisely the contribution over the MMIO + driver baseline the task critiques.

Non-speculative dispatch via strongly-ordered device memory — a real ISA mechanism

Marking the dispatch STRICT_ORDER makes it fire only when the instruction is non-speculative, on every host model (in-order head-of-pipeline gating; out-of-order commit-time handling). This is faithful RISC-V — the same family as acquire/release and FENCE — not a simulator hint. It cannot be expressed as a memory-region (PMA) attribute, because the dispatch targets the operand in ordinary main memory, so the ordering correctly belongs to the instruction.

The fence is a single-core coherence problem, and it stays simple

Because the second agent is a memory-side engine (not a second core), there is no protocol, no snooping — just point cache-maintenance from the one core: clean before, invalidate after. The hazards map one-to-one onto the two fence variants, and reuse gem5's existing, faithful cache-maintenance path.

Completion belongs to a batch, not to a MAC — one bit expresses it

A GEMV is never one dispatch: the matrix does not fit in one DRAM row, so it decomposes into many MACs spread across engines. With completion reported per MAC, host notification cost grows with the work and never amortises. Scoping completion to the batch instead — one encoding bit marking the closing dispatch — decouples the two. Verified: three MACs on three engines with the bit set only on the third produce three MACs of work and one completion event, exiting cleanly. The reported completion was confirmed genuine rather than a preemption artifact by matching it to the MAC's own finish cycle (DRAM clk 1604 observed against 1605 predicted from tCCD_L × (num_macs + pipeline − 1)).

One dispatch occupies one engine — and a second MAC there is preemption, not accumulation

Established from the platform: one MAC command drives all four banks of one bankgroup (one PRECHARGE + four ACTIVATE at tRRD spacing before a single MAC issues), giving 8 KB per dispatch across 32 engines (2 ranks × 4 bankgroups × 4 channels). num_macs is bounded by one row at 64 steps, and the per-dispatch row setup is 11% of dispatch latency and does not amortise — which is why 64 is the design point rather than merely the limit. Critically, the engine holds one MAC at a time: a second MAC arriving at a busy engine is modelled as preemption, consistent with the interrupt-preemptible PIM model. Batch-scoped completion is therefore expressible; several MACs accumulating into one accumulator is not, without changing the memory model itself.

Out-of-order finding: busy-poll completion self-deadlocks — and the ISA-level wait resolves it

On an out-of-order core an interrupt can only be taken at a precise boundary — a point where every earlier instruction has retired and no later one has begun. With many instructions in flight no such point exists, so the core must first drain (commit.cc: "wait until all in flight instructions are finished before enterring the interrupt"). A completion poll-loop therefore deadlocks against itself: the loop is what keeps the pipeline occupied, so it prevents the very interrupt it is waiting for. This is direct evidence that ad-hoc MMIO/driver polling is inadequate on a realistic microarchitecture — the deadlock is a property of the microarchitecture, not of the driver's coding style.

Resolved, and it takes two mechanisms working together. First, the wait instruction is marked squash-after, so retiring it discards all younger instructions and empties the in-flight list for one cycle — that window is the precise boundary at which commit takes the interrupt. Second, it must not sleep once the interrupt has already arrived: posting an interrupt sets a pending bit and issues a single wake-up in the same action, so a core that sleeps afterwards has missed a one-shot event and never wakes. The wait therefore sleeps only while no enabled interrupt is pending, and spins one iteration otherwise. Both conditions are the same ones RISC-V's own wfi observes.

Measured: the out-of-order core completes the full dispatch → wait → completion → fence → exit flow at 470 committed instructions — identical to the in-order model, satisfying the cross-model instruction-count invariant, and spends 247 cycles quiesced of the 290-cycle MAC window. It genuinely sleeps rather than busy-waits, which is the energy-correct idiom for edge inference and the behaviour the instruction exists to provide. Note the squash-after property is load-bearing for interrupt delivery, not a scheduling optimisation — a durable hardware-contract requirement rather than simulator glue.

How it was evaluated

Methodology

  • Simulator. gem5 v25.1.0.1, RISC-V full-system, driving the PIMony DRAM-PIM model (interrupt-preemptible; MAC engine is timing-faithful with no arithmetic, so correctness is demonstrated at the transaction and ordering level, not by a computed value).
  • Bring-up path. Bare-metal ELF tests for each instruction, then a full-system boot → checkpoint → restore pipeline to reach a timing region of interest quickly.
  • Verification. Cache/DRAM transaction traces confirm A/B-equivalence of the fence to standard cache-maintenance ops, single-dispatch behavior, and correct write-before-compute / read-after-completion ordering; pipeline traces confirm the non-speculative and interrupt-injection behavior on each model.
  • Cross-validation of timing. Device-side and host-side time bases are reconciled independently rather than assumed: dispatch latency decomposes into 33 DRAM cycles of row setup plus 276 of MAC execution, and 309 DRAM cycles × 0.937647 ns reproduces the 290 host cycles measured from gem5 at 1 GHz. Completion events are likewise attributed by matching the observed cycle against the MAC's predicted finish, which distinguishes a genuine completion from a preemption event.
  • Claim discipline. Per-event costs are reported as measured; workload-scale projections are reported only where a run supports them. Where the model is structurally unable to exhibit a hazard — accumulator corruption and early-completion races, both of which require computed values the timing-only MAC engine does not produce — that is stated rather than inferred from a passing run.

Where it goes next

Open items & next steps

  • "This one is done" vs "all are done". The completion bit reports the MAC that carries it, which equals batch completion only when that MAC finishes last. It holds under uniform num_macs and in-order issue, but refresh, row conflicts and memory-first scheduling perturb start times. Candidate fixes: a multi-token wait (the per-token scoreboard is already a bitset) or a monotonic completion counter — the latter is order-independent, costs one register and one comparator, and matches established practice (DMA tag groups, GPU fence values, expected-transaction barriers). Note this would be a real-hardware correctness bug that the timing-only model cannot exhibit.
  • Quantifying the notification saving. The per-event costs are measured (290 cycles per MAC, 1361 cycles per handler entry, single dispatch). The scaled saving is not yet measured and is not claimed here: because the completion line is a latched level held until the done-mask is acknowledged, several completions can be retired by one handler entry, so the handler-entry count is an empirical quantity rather than the completion count. The settling experiment is a multi-dispatch run comparing completions against handler entries.
  • Narrow the sleep condition. The wait currently declines to sleep while any enabled interrupt is pending — correct for wfi, too broad here. On a system with a periodic timer something is nearly always pending, so it would spin rather than sleep and the energy argument would be lost. The condition should test the PIM completion source specifically. Not yet exposed, because the bare-metal tests run without a timer — which is precisely why it needs fixing before the overlap study.
  • Completion granularity in the device. Completion is currently signalled at channel level; the per-bankgroup path exists and is unused, and is required before concurrent batches can be tracked independently.
  • Overlap evaluation. The core quantitative study — independent host work executing concurrently with the asynchronous MAC — which is an out-of-order story and the reason the O3 path matters.
  • RTL-level validation. Confirm the instruction contracts against a hardware implementation where feasible, distinguishing the durable hardware contract from simulator-side modelling glue.

Framing

The three instructions are the durable contribution: a named, analyzable interface for asynchronous DRAM-PIM. The MMIO + driver approach is retained deliberately as the baseline to compare against — and the out-of-order deadlock is a first concrete result showing why the ISA-level primitives are needed, not merely convenient.
