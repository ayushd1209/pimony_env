Design record · MSc thesis · PIMony / gem5 v25 · rev 8

pim.gemv

A coarse-grained RISC-V instruction that offloads a whole matrix–vector product to DRAM-PIM. This is the decision trail: what the hardware forces, what was chosen, what has actually been measured — and which earlier conclusions were overturned. Rev 7: the in-order host. On gem5’s in-order Minor core the speedup is 16.54×, against 17.53× on O3 given the same vector unit; TimingSimpleCPU’s 8.43× is the outlier, because it blocks on every memory access. The widening comes from having a pipelined host at all, and out-of-order execution adds only 6–12%. Rev 6 credited the widening to out-of-order overlap of PIM’s host work; that mechanism is withdrawn. Rev 8: on GPT3-2.7B the order flips — 28.29× on Minor against 22.81× on O3 with the same vector unit — so the host comparison is quoted per workload.

⚠ O3 figures superseded (2026-10-02). gem5’s O3 let later accesses pass pim.fence before its clean or invalidate had happened (GAPS_pim_gemv.md G13, fixed in ed427c0). After the fix, matmul-only speedups are BERT 16.54× on Minor vs 12.59× on default O3 (14.13× with Minor’s vector unit) and GPT-3 28.29× vs 16.24× (18.95×). Every O3 figure on this page predates the fix; the Minor and TimingSimple figures stand.

PART 0

The result, if you read nothing else

Rev 7: the whole layer, on an in-order and an out-of-order host

bert.c issues eight pim.gemv in place of its six linear() calls — a whole BERT-base encoder layer, batch 1, offloaded with interrupt-driven completion, and since rev 6 the host reads the results back, sums W2’s three partial vectors and pays the FP16→float conversion. Same CPU, same caches, same clock, confirmed from each run’s config.ini.

The speedup is a property of the host. Quote it with the CPU model attached, always. TimingSimpleCPU and O3 differ in two ways at once — O3 is pipelined and out of order — so rev 7 adds the host that separates them: Minor, gem5’s in-order pipelined core.

The mechanism behind the speedup is unchanged from rev 5 and is the L2: 54,856 demand misses against 1,021, because the weights stop crossing the memory bus to reach the core at all.

Why a better host widens the advantage

This is the opposite of the usual expectation — an accelerator is supposed to look best beside a weak CPU. Moving off TimingSimpleCPU helps PIM 2.34× and the baseline only 1.19× on the in-order Minor, and 4.27× against 2.31× on O3. The widening is already complete on the in-order core, so it is not out-of-order overlap. The IPCs say what it is:

Rev 8: on GPT3-2.7B the order flips. The same comparison on the GPT-3 decode layer gives 28.29× on Minor and 22.81× on O3 with the same vector unit. Out-of-order execution speeds that baseline up 2.12× (BERT-base: 1.71×), because it keeps more L2 misses in flight — 6.8 on average against Minor’s 1.5 — but speeds the PIM run up only 1.71×, because 72% of that run is the host asleep while the device works. So “a better pipeline buys a memory-bound baseline little” holds; “out-of-order buys it little” does not. In absolute time O3 with pim.gemv is still the fastest system on both workloads.

So the parked “best host for an async PIM” question has a milder answer than rev 6 gave: any pipelined host roughly doubles PIM’s advantage over a blocking one, and out-of-order execution adds 6–12%. Caveat: Minor and O3 are gem5 configurations, not modelled cores. Say “on an in-order host” or “on an out-of-order host”, never “the instruction is 17×”.

Why O3 had to be given Minor’s vector unit

Which side is the bottleneck — and it changes with the host

Rev 5 retired two lines of work on the strength of that 5.6%. One of those retirements is now reversed. It read: “further PIM-side optimisation is worth ≤6%, and so is overlapping host work with PIM work.” On a real host the second half is backwards. 41.8% of the layer is dead host time, which is exactly what an async offload exists to fill — and pim.dispatch returning a token while pim.wait blocks separately was built for it from the start. Nothing has ever used it that way.

The first half still stands, and more strongly: host-side optimisation now buys little, because CPU busy time is only 58% of the layer and the PIM would simply wait longer. What used to look like the obvious target — pim_store_vec, 80% of CPU busy time — is the smaller prize.

What the result path costs, both halves

Rev 6 closed the last hole in the ISA: pim.gemv had no output address, so results were computed and discarded. Adding out_base, the sequencer’s write-back, and the host-side read-back gives both numbers for the first time.

Completing the result path cost +23.7% of the layer and took the in-order number from 11.3× to 8.24×. State it that way round: the speedup fell because the workload became complete, not because the design got worse.

Quote this as batch-1, never as “BERT”. At SEQ=1 there is no weight reuse; arithmetic intensity rises ~71× by SEQ=128 and PIM’s case is gone by SEQ≈64. Batch 1 is the decode-shaped edge case the workload partition deliberately targets.

The earlier result: both big improvements lived below the interface

Between rev 1 and rev 3 the implementation changed enormously. The instruction did not change at all.

One row above has since been overtaken. “Software above the instruction — no change” was true across rev 1–3 and is false now: D13 moved the two base addresses into a descriptor in memory, so rs1 became a pointer, and the bert.c integration added the descriptor fill, pim.fence.cl and pim_store_vec. That does not weaken the argument below — the encoding and the shape operand never moved, and neither microarchitectural fix touched software. It does mean the claim must be stated as “the two scheduling fixes were absorbed below the interface”, not “software never changed”.

Both improvements lived entirely below the interface. That is the empirical case that a coarse pim.gemv is the right granularity, and it is a stronger claim than “it is faster”. A per-MAC ISA could not have absorbed either fix: in that design the CPU is the sequencer, so the four-outputs-per-command discovery and the breadth-first ordering would both have surfaced as software changes.

Paired with D1 — per-MAC dispatch is issue-bound — this gives both halves of the argument: the fine instruction is wrong because it cannot be fed, and the coarse one is right because it absorbs microarchitectural change.

The rev-4 result that rev 6 invalidated

The 25% readout cost was measured with 4× too many readouts — it is about 11%

Everything in this subsection was measured while the sequencer issued one READRES per bank instead of one per bankgroup. The 62 cycles below is explicitly “four serialised readouts”; there is one. So the 25% figure, and the RTL recommendation it produced — add a second result register per bank — both rest on a defect.

Kept rather than deleted, because the reasoning is still right and is the transferable part: occupancy is not cost, and a stream blocked on its own readout is a latency problem, not a bandwidth one. Re-measured on 30 September with one READRES per bankgroup: a clean compute round is 274–280 cycles against 248 with no readout, so the stall is about 30 cycles, about 11% instead of 25%. The second result register survives as a recommendation at half the size. Building it is PIM-hardware work, outside the scope of this thesis.

The readout phase was estimated at ~13% of the compute loop. Measured, it came out at 25% — and the reason the estimate was wrong is the part that survives.

That 62 cycles exists because each bank has one result register, so a unit cannot begin its next dot until the current result has been read out. So the measurement puts a number on that assumption: a second result register per bank would remove most of the stall — 25% as first measured, about 11% once the over-issue was fixed. That is a concrete RTL recommendation derived from measurement rather than from intuition — a better outcome than the estimate would have been if it had been right.

PART 1

What the hardware forces

Every decision downstream follows from four facts. They are not design choices — they come from LPDDR5X_12Gb_x16_8533_pimony.ini, from PIMony's source, and from the PIMony paper. Where those three disagreed, the paper won; Part 6 records where that changed an earlier conclusion.

01

The memory is a tree. Commands go to bankgroups; arithmetic lives in banks.

channels = 4, ranks = 2, bankgroups = 4, banks_per_group = 4. Two different counts matter, and conflating them was the single biggest error in the first revision of this document:

The control logic then broadcasts MAC signals and addresses from the counter to all banks in the designated bank group, incrementing the counter every tCCD_L cycles. Multiple bank groups can be driven simultaneously through bank-group select signals.

PIMony paper, control logic for interrupt-based PIM

A bank holds 49,152 rows of 2 KB, and a row must be ACTIVATEd before any of it is readable. Reading a different row costs PRECHARGE then ACTIVATE.

02

An address is a set of coordinates, and channel is the lowest field

address_mapping = rorabacobgch, read low bits first, chops a byte address into one field per level of the tree:

Measured strides, derived from the ini and confirmed against Config::AddressMapping:

03

A MAC command sweeps columns within one activated row

… the control logic detects the command and initializes the corresponding bank-group counter (BG CNT) with the column address where the MAC operation begins.

PIMony paper

The counter is a column counter. So num_macs is a count of column steps, the sweep stays inside the activated row, and the 64-step ceiling is a physical consequence rather than an addressing quirk. A dot longer than 64 steps needs a second command and a row change.

04

A second MAC to a busy bankgroup means RESUME, not queue

Two lightweight commands, MAC and MAC_INTR, are introduced… MAC_INTR temporarily halts MAC execution in the targeted bank group. After serving the request, a subsequent MAC command resumes the remaining computation.

PIMony paper, interrupt-based PIM mechanism

So the sequencer must never issue to a bankgroup that is still computing: the command would be read as a resumption of work that was never halted. This was found by measurement before it was found in the paper — see Part 4.

PART 2

The operand layout

This is the crux of the design. A dot product accumulates into one bank's result register, and there is no command that combines results across banks. So the placement of weights is not an optimisation — it decides whether the computation is possible at all.

The proof that a dot cannot cross a bank, from code alone

Rev 1 spilled a long dot from one bank into the next. The paper's per-bank result register rules that out, but there is a second, purely code-level argument that needs no paper at all — and it is the one to use, because it is checkable in ten seconds:

Read forwards, the same fact is the useful one: a command reaches all four banks, so it computes four different outputs at once. The fact that kills spillover is the fact that gives 4× parallelism.

PART 3

Decisions and their justification

D1

The bottleneck is issue bandwidth, and only the ISA can fix it

measured
Claim
Per-MAC dispatch cannot feed the engine array. At 75 cycles per pim.dispatch, BERT's linear layers spend far longer issuing than computing.
Why no microarchitectural fix exists
O3 measured only 4% better than in-order (75 vs 78 cycles). The instruction's STRICT_ORDER flag makes the LSQ handle it one at a time, and that flag is load-bearing — removing it crashes the cache. The cost is architectural.
Evidence
16 back-to-back dispatches, 11 identical steady-state gaps on each CPU model, tests/test-progs/pim_issue/.
D2

One instruction carries a whole matmul

measured
Claim
Six pim.gemv per BERT layer (eight, with W2 split). The CPU issues one instruction and stops.
Status
Working end to end: a single instruction expands into 192 MAC commands for a 768×768 matmul and completes correctly (Part 4).
The stronger form of the claim
See Part 0. The command count fell 8× and utilisation rose from 4.1% to ~70% without the instruction changing. The interface absorbed both.
Precedent
gem5-CIMD passes rowadd(dst, a, b, size, n) — problem size and element width, never a parallelism figure. The memory controller decides the mapping.
D3

The operands are a base address and the matrix shape

design
Encoding
pim.gemv rd, rs1, rs2, custom-0 funct3=5, encoding 0x00B5560B for a2, a0, a1. rs1 = weight base; rs2 = dot_steps | num_outputs<<16; rd returns the token.
Nothing about the DRAM configuration is encoded
A pointer and two model dimensions. The base must be aligned to the row stride — a hardware property the instruction refers to without naming a number, as a vector load requires element alignment without naming a byte count.
Why two numbers
A matmul is two-dimensional and one total cannot express it: 589,824 weights could be 768 dots of 768 or 3072 dots of 192. Four matrices are square; W1 and W2 are not.
Why registers, not immediates
~6 spare encoding bits versus 22 needed. Registers also keep the instruction model-independent — the same binary runs d=2560.
D4

PIM-gathered operands are part of the instruction's contract

design
Claim
pim.gemv requires the layout in Part 2. A row-major matrix is not slow — it is uncomputable, because each dot's accumulation would be split across accumulators that cannot be combined.
Why it is free
Weights are static, so the permutation happens in init_params() before m5_reset_stats(). Zero runtime cost.
Precedent
SIMDRAM and gem5-CIMD both require operands in a reserved pool from a custom allocator. Comparable to alignment requirements on a vector load.
Enforcement
A misaligned base, an over-long dot, a degenerate shape, or an unexpected address_mapping stop the run with a diagnostic rather than computing silently wrong addresses. This is not decorative — it caught a stale test binary on the first rev-3 run.
D5

The sequencer drip-feeds, because PIMony has no backpressure

measured
Claim
MACs are issued at most one per DRAM cycle and only when WillAcceptTransaction reports room.
Why the check is mandatory
The queue holds 96 per channel, shared with ordinary CPU loads. AddMACTransaction returns true unconditionally, and PIMony is built Release so -DNDEBUG compiles its own asserts out. An overflow would drop the MAC silently — the token never completes and pim.wait hangs forever.
In RTL
~100 flops plus a comparator; address generation is field concatenation, since every stride is a power of two. Use two counters rather than one cursor, to avoid the divider the C++ model uses for clarity.
D6

Never issue to a bankgroup that is still computing

measured
Claim
One bit per stream, set on issue and cleared when that MAC's response returns. A command sent to a busy bankgroup would be interpreted as resume (Lesson 04), not as queued work.
Evidence
Isolated minimally: 1 stream + 1 command passes, 1 stream + 2 commands aborts, with the same address and nothing else changed.
Cost, now measured
The gate is what the residual ~23% idle is: 248 cycles between successive MACs on one stream against 192 cycles of work. The 56-cycle difference is drain → callback → re-issue turnaround, not DRAM.
D7

Completion is decided by counting drains, not by flagging the last MAC

design
Claim
Every MAC carries comp = 0. The sequencer counts outstanding commands and raises the interrupt when the count reaches zero and nothing remains to issue.
Why
The streams drain independently, so issue order is not completion order — the last MAC issued can finish before an earlier one. Flagging it would wake pim.wait while units were still running.
D8

A dot must fit one row; longer reductions are split in software

design
Claim
The contract is one dot ≤ 64 column steps = 1024 FP16 elements, checked at entry. W2's 3072-long reduction becomes three pim.gemv over 1024 inputs each, and the host sums the three partial vectors.
Why not carry the accumulator across rows
That would require the running sum to survive a PRECHARGE. PIMony cannot answer this — it has no accumulator — and the paper describes resume only for the preemption case. The instruction is deliberately specified not to depend on an unresolved hardware question.
Cost
1,536 host additions against 2.36 M MACs, plus 3× readout for W2. K-splitting a long reduction is standard practice in tuned GEMM libraries.
Why the partials are stored as separate blocks
Interleaving them (partial p at rows wave*3+p) would force two extra operands — the placement stride and the partial index — into the instruction. Storing three independent row-aligned blocks keeps pim.gemv at two operands, with the same footprint. The split lives in the layout, not the ISA.
D9

Breadth-first issue is a scheduling policy, not part of the ISA

measured
Claim
Consecutive commands go to different streams: stream = cmd % 32. All 32 fill before any is revisited.
Effect
Utilisation 4.1% → 65–77%. Depth-first leaves 31 streams idle behind the D6 gate.
Why it matters architecturally
The same instruction runs correctly under either order — just slower. This is the cleanest single demonstration of Part 0: a large performance change with a zero-byte ISA diff.
Issue stays in order
A single issue port that skipped busy streams would need a full scoreboard. Breadth-first already means the next command is on a different stream, so the gate rarely blocks until all 32 are in flight. PIMony's own command queue then reorders around DRAM timing, downstream of us.
D10

MAC and READRES interleave per stream, not as two global stages

measured
Claim
A stream that has finished multiplying reads its four results out and starts its next dot while other streams are still multiplying. There is no global “all MACs, then all readouts” barrier.
Why
A global barrier would make all 32 streams wait for the slowest one every wave. The hardware does not require that — each bankgroup's results are independent. This is the same class of mistake as the depth-first ordering that cost 4.1% utilisation, and it was nearly made a second time.
Consequence for the busy gate
A stream is not free when its MAC drains — it still holds four unread accumulators. The D6 bit therefore stays set from MAC issue until the last readout drains.
D11

The input vector is loaded from DRAM (D2GWRITE), not pushed by the host

design
The choice
Two commands can fill the global buffer. H2GWRITE takes the vector from the host over the bus. D2GWRITE reads it out of a DRAM row that the CPU wrote earlier.
Why D2GWRITE, and it is a fidelity argument not a performance one
With H2GWRITE, the host's push of 1536 B is performed by nothing in this model — gem5's CPU never issues those stores, PIMony simply charges 128 cycles and invents the data. That would make PIM look free. With D2GWRITE every cost is carried by a mechanism the simulator actually runs: the CPU really writes the vector, pim.fence.cl really pushes it out of the caches (57 cycles, measured), and the D2GWRITE really reads the row.
What this does not buy
It does not save data movement. The fence crosses the bus either way. State it as fidelity, never as a bandwidth win.
Consequence — and this is the good one
pim.fence.cl stops being an optional coherence tool and becomes a required step in the offload sequence. The third instruction turns out to be load-bearing rather than a convenience.
D12

The input vector is stored four times, once per channel

measured
Claim
The global buffer is per channel. A channel's buffer can only be filled from that channel's own DRAM — there is no wire from channel 1's array to channel 0's buffer. So one pim.gemv issues four D2GWRITEs, and the vector must exist four times in memory.
Evidence
The paper: the GB broadcasts the input vector to all banks within the DRAM channel. PIMony's code alone was ambiguous — its timing tables key the exclusion on rank (suggesting 8 buffers) while queue admission discards rank entirely (suggesting 4). The paper settled it; the rank-keyed table is conservative exclusion, not a statement about where the buffer lives.
The cost is smaller than it sounds
Channel stride is only 32 B, so the four copies interleave inside one DRAM row. Four copies cost one row, not four.
Alignment
The vector needs only 32 KB alignment, weaker than the weights' 256 KB, because its offsets never touch the bankgroup/bank/rank/row fields. What breaks it is nonzero column bits: at a 512 B base a 48-step vector still works, but W2's 64-step part spills past column 63 into the next bank.
D13

The operands travel in a memory descriptor, not in MMIO registers

design
The problem
A memory request carries one address; this offload needs two. The bind is not the RISC-V encoding — it is what reaches the memory side: a 64-bit packet address plus a single 64-bit sideband word. 128 bits available against 192 needed, and the deficit is exactly one address.
Decision
Pass a pointer to a descriptor in memory holding weight base, vector base, and shape. The instruction stays pim.gemv rd, rs1 with rd returning the token.
Why, and this is the deciding evidence
The thesis task description names the alternative as the thing to be replaced: “Existing prototypes address these gaps through memory-mapped I/O and ad-hoc driver conventions, which neither compilers nor microarchitectures can reason about for correctness, ordering.” MMIO is therefore not an available option for a core operand — choosing it would undercut the premise of the work.
Why a descriptor is analyzable, where MMIO is not
With MMIO the vector address arrives through a side channel the instruction never names: no register dependency, so neither the pipeline nor a compiler knows the store and the offload are related. With a descriptor the pointer is a real source operand, the struct is ordinary memory a compiler already models, and the ordering requirement is expressed by an ISA instruction — pim.fence.cl — rather than by convention. The task's objection is to unanalyzable ordering, not to operands living in memory.
Why not a CSR
A CSR is CPU-side state and cannot reach the memory controller on its own. Making it fit means evicting the shape from the descriptor and packing the vector address into the freed bits, which only works because the vector is 32 KB aligned — a fact about this DRAM part. That puts memory geometry inside the encoding and violates D3. Rejected on our own rule, not on taste.
Second-order benefit
Keeps the extension at three instructions — dispatch, fence, wait — matching the brief. Carrying the address in a fourth instruction would exceed it.
Convergence worth noting
pim.fence.cl is now structurally required by two independent routes: the input vector must be flushed for D2GWRITE (D11), and the descriptor must be flushed before the device reads it. A fence that was designed as a coherence tool has twice turned out to be load-bearing.
The cost that must not be allowed to vanish
The device has to really fetch the descriptor. gem5 makes a functional read easy, and a functional read is free and instantaneous — the identical trap rejected in D11. The fetch must be a timed read with a wait state in the sequencer, or the descriptor becomes a cost performed by nothing.

One of those five predictions validated nothing

8,448 readouts was our own defect, not a measurement. The sequencer issued one READRES per bank; READRES has no bank field and names a bankgroup, so three of every four commands were indistinguishable on the wire. The correct count is 2,112, one per MAC command — measured after the fix, with no preemption abort.

It matched because the prediction was derived from our own design rather than from the spec: it checked our arithmetic against itself. The other three stand precisely because they were not — 110,592 comes from the weight matrices two independent ways, 32 from the instruction count times channels, 8 from the instruction count. A prediction only validates when it is derived independently of the thing being tested.

Settled by the paper’s CA table: the READRES row carries BG1 BG0 and leaves the bank positions blank, where the Precharge row above it fills them in. Confirmed by PIMony’s own reference generator, LLM.cc, which emits exactly one READRES per MAC at the MAC’s address.

inst.quiesce counts actual sleeps (System::Threads::Thread::quiesce), not executions of the instruction — so it is a two-sided check. Fewer than 8 would mean a pim.gemv completed before its wait, i.e. launched nothing; more than 8 would mean a spurious wake. It costs nothing and should be read on every PIM run.

There is no MAC command counter in PIMony. Use num_comp_cmds: it is incremented by cmd.num_macs per MAC and only when is_first_comps, which originals carry and preemption resumes do not — so it counts issued work and is immune to the resume effect measured earlier.

Two traps that both produce a confident wrong answer

A gem5 stats reset wipes PIMony’s counters, and PIMony only writes its stats file on the exit callback. Ending the ROI with m5_dump_reset_stats() therefore zeroes every count before it is ever written — the file reads all zeros, which looks exactly like “the PIM did nothing”. Use m5_dump_stats() (0x8200007B); the first stats block is unchanged, because the reset at ROI start is what scopes it. Those files are also written to the gem5 root, not the output directory, and the next run overwrites them.

numCycles is not comparable across CPU models — and this one actually fired. On TimingSimpleCPU it is whole runtime; on o3 and minor it counts active cycles only, so the time the core sleeps in pim.wait vanishes. That is fatal here because PIM sleeps and the CPU baseline does not: on O3, PIM’s 96,978 quiesced cycles were dropped while the baseline lost nothing.

Ratio from numCycles: 28.51×. Ratio from simTicks: 15.28×. The first was published and corrected the same day. Derive every cross-CPU number from simTicks (÷333.33 for cycles at 3 GHz); same-CPU A/Bs are safe with numCycles. Worth noting that this warning already existed, in these words, before there was a number for it to protect — a known trap written in a note is not a guard.

PART 5

The full operation, and the one phase still missing

A GEMV is three phases, not one. Rev 3 modelled only the middle one. Rev 4 adds the readout; the load phase is designed and verified on the software side but not yet issued by the sequencer.

1 · D2GWRITE x 4
Loads the input vector into each channel's global buffer, from which it is broadcast to every bank. One per channel (D12). Every unit multiplies against the same x, so it is a broadcast, not a per-unit copy.
next
2 · MAC x N
Multiply-accumulate weights against the broadcast vector, into each bank's result register.
working
3 · READRES x 4N
Takes each accumulated result out of its bank. Interleaved with the MACs per stream, not run as a global stage (D10).
working

The entry point that blocked phases 1 and 3 turned out to be trivial. AddMACTransaction hardcoded MemoryAccessType::MAC; it is now a wrapper over a general AddPIMTransaction(type, …). The two enums involved — gem5's MemoryAccessType and PIMony's TransactionType — are declared member-for-member in the same order, so the cast is valid for every command type. The other four commands were unreachable because of one hardcoded argument, not for any deeper reason.

What is still missing, and what it blocks

The GWRITE phase falls straight through — so today every MAC multiplies against a global buffer that was never filled. Because PIMony performs no arithmetic, nothing detects this; adding the phase can only change timing, never a result. That is exactly why it would be easy to skip and why skipping it would flatter PIM.

How the vector's address reaches the sequencer is decided but not built — see D13. A memory descriptor, because a request carries one address and this offload needs two, and because the task description rules out the MMIO alternative by name. What remains is implementation: a timed descriptor fetch as a new phase ahead of GWRITE.

READRES is not bank-aware — the correction that cost 4×

The rule that falls out: the CA encoding is the spec. A simulator’s internal representation is implementation, and a code comment asserting otherwise — this one said “unlike MAC the bank field here is load-bearing” — is not evidence. It is the same failure mode Part 6 records for every other correction: reasoning about hardware semantics out of simulator data structures.

Confirmed three independent ways before the change: the CA table; PIMony’s own trace generator LLM.cc, which emits one READRES per MAC; and the controller itself, where a READRES does only three things — timing constraints, a stat increment, one return-queue entry — and never touches mac_states_. PIMony has no opinion on the count.

The estimate that was wrong, kept because the error is instructive

Rev 3 predicted the full sequence would cost ~13% of unit time, built up from bus occupancy. The measured figure is 25% on the compute round, and about 11% once the 4× over-issue was fixed (rev 7), which happens to sit close to the estimate. The table below is the old estimate; it is left standing because the shape of the mistake matters more than the number.

Why the estimate was wrong. It costed the readout as throughput on a shared bus. The readouts do only occupy the bus for about 6 cycles — that part was right. But a stream cannot start its next dot until the last of its four readouts has drained, so the cost lands as latency on the critical path: 24 cycles of pipeline drain plus four serialised readouts, about 62 cycles inside a 248-cycle round. A resource can be almost idle and still be what everything is waiting for.

What the 62 cycles actually prices. It exists only because each bank has a single result register. This was flagged in rev 3 as an assumption; it is now a measured quantity, and it converts directly into an RTL recommendation — add a second result register per bank and most of the stall disappears: about 11% of a compute round with one READRES per bankgroup, not the 25% measured at 4× over-issue.

PART 7

Limitations to state up front

  • A timing study, not a numerical one. PIMony's MAC performs no arithmetic and MacState has no accumulator field — grepping PIMSim/src for accum|psum|partial_sum|result_reg returns nothing. Everything here verifies placement and timing, never numerical correctness. This is exactly why rev 1's ladder passed with a broken layout.
  • The speedup is a property of the host, and must never be quoted bare. 8.43× on TimingSimpleCPU, 16.54× on in-order Minor, 17.53× on O3 with the same vector unit (15.60× with O3’s own). Minor and O3 are gem5 configurations, not modelled cores, and they are matched on the vector unit only; a ROB/LQ sweep would turn them into claims about machines. On GPT3-2.7B the order flips: 28.29× on Minor, 22.81× on O3.
  • On BERT-base the out-of-order gain is a range, 6–12%. It moves with code layout, and it is an upper bound, because Minor’s single unit also slows scalar FP. Quote the range, never one of its ends.
  • The result width is an assumption, not a reading. The paper gives operand widths — 16 FP16 from the BLSA, 16 from the global buffer — but never a result or accumulator width, in Fig. 1, the DPSA section or the area section. FP16 is our choice. Sensitivity is one constant and would take result traffic from 0.77% to ~1.5% of a layer, so no conclusion depends on it. The absence itself is worth stating: a 1024-term dot accumulated at operand precision is a real hardware question the paper leaves open.
  • pim.wait returns when result writes are accepted, not when they reach the array. Deliberate: real posted-write buffers behave the same and rely on forwarding for correctness. An examiner will ask, so state it rather than be asked.
  • The write-back’s loopback is unmodelled. Data returned on one channel’s bus must be re-issued as a write on another’s — a real loopback plus a write-combining buffer. gem5 charges nothing for it. Same bucket as the self-clean freebie: a hardware contract, never a free lunch.
  • Under PIMony’s PIM-first policy the PIM jobs ran 20.6% slower. Open, not traced. Suspected: the sequencer’s result write-back is an ordinary write, which PIM-first holds back while that bankgroup has PIM work queued — including the sequencer’s own MACs. If confirmed it is a contract point: result write-back must not queue behind the PIM work it completes.
  • PIM-first can livelock PIMony’s DRAM model. A D2GWRITE and a CPU read on one bank, in different subarrays, close each other’s row one cycle after it opens: the model times the close by the requester’s subarray, so tRAS is skipped and neither request ever reaches its column command. A model bug, not the design; documented, not patched.
  • The fences’ ordering has never been exercised. pim.fence.* carry IsReadBarrier + IsWriteBarrier, which is a deliberate divergence from Zicbom, where cbo.clean carries none and ordering is a separate fence. On an in-order CPU the barrier is a no-op, so the semantics are declared but untested.
  • The GWRITE's own completion is free in this model. PIMony drops num_macs when it builds a D2GWRITE command, so the transaction completes in zero cycles. The cost is not lost — the exclusion tables still hold following MACs for 128 cycles, and the row activation is charged through the normal bank state machine — but the phase transition will fire sooner than intuition suggests.
  • A GWRITE does not delay MACs in the other rank of its channel. The exclusion tables have no different-rank entry for D2GWRITE. If the buffer is channel-wide, arguably they should. PIMony's internals are out of scope, so this is stated rather than patched.
  • Marshalling the input vector is real host work. Four scattered copies means 4n stores per matmul — about 3,072 for a 768-long vector, against 590k MACs. Small, but it is on the critical path and belongs inside the timed region, not hidden in setup.
  • The 4.1% → 77% figure is not like-for-like. Different shape and precision. Report the two wins separately.
  • Short-context design. Linear layers dominate only while the sequence is short; crossover is at SL ≈ 6d, so ~4,600 tokens for BERT-base. The partition — PIM does QKV and FFN, CPU-V does attention — rests on dot-product length and operand mutability.
  • FP16 requires re-baselining. -DPIM_FP16 gives an FP16 CPU baseline, but the tuned-library comparison has not been redone at FP16.
  • Memory padding. 1.33× for 768-long FP16 dots. Address space, not time, but it is a real architectural cost of the one-dot-one-row rule.
  • The 64-step cap is honoured by choice. The vendor's own clamp sits commented out at pim_controller.cc:769; the model would accept a longer sweep and bill for it.
  • One GEMV in flight. A single GEMV already spans every stream, so concurrency would add state without throughput.
  • tFAW may not apply to MAC activations. The ASYNC path returns its ACTIVATE without calling ActivationWindowOk, which the ordinary read/write path does check.
  • A latent abort worth avoiding. bankstate.cc:385 has case ACTIVATE: under State::OPEN with no break, falling through to AbruptExit. It should never fire, but a sequencer bug would kill the run rather than warn.
