# PORT_PLAN — PIMony / custom-RISC-V gem5 fork: v23 → v25.1.0.1 (FS-mode-ready)

## 1. Executive summary

Overall risk is **LOW-to-MEDIUM**. Five of seven surfaces are low-risk: the custom diff is small, isolated, and grafts onto v25 anchors that are structurally unchanged (the decoder graft slot `OPCODE5=0x02`, the `PIM_DISPATCH=0x08000000` Request flag, and the RISC-V ISA token-scoreboard members all paste in cleanly; bit and decode-slot availability were grep-confirmed in v25). **Effort is dominated by two surfaces**: the **gem5↔PIMony glue** (medium — five forked `pimony.*` files must be re-vendored as a renamed fork of v25 `dramsim3.*`, not 3-way merged, plus two SConscripts re-grafted and a SimObject class-name collision managed) and the **build/config + vendoring** surface (medium — re-grafting both SConscripts in the right order, porting `PIMony.py` onto v25's `DRAMsim3.py`, re-initialising 4 external submodules, rebuilding `libdramsim3.so`). The **FS-mode payoff clearly justifies the port**: v25 brings a PMP checkpoint/restore serialization fix (v23 silently loses PMP CSRs on restore), the H-extension two-stage walker, `RiscvBootloaderKernelWorkload` for real Linux boot, and richer fault codes — none of which conflict with the custom work because the PIMony diff touches **zero** FS-mode files. The one real caveat: v25 still walks only **Sv39** (3 levels) despite SV48/SV57 enum entries, so an Sv48 Linux image must be forced to Sv39 or the walker extended.

## 4. New FS-mode surface gained (upgrade benefit — zero merge conflict)

The PIMony custom diff touches **none** of the FS-mode files, so v25's FS infrastructure comes for free:

- **PMP checkpoint/restore fix** (`src/arch/riscv/pmp.{cc,hh}`): v23 had **no** PMP serialize/unserialize — PMP CSR state was silently lost on restore. v25 makes `PMP` override serialize/unserialize and `PmpEntry : Serializable` (rawAddr + pmpCfg per entry). **Load-bearing if you fast-forward past Linux boot via checkpoint/restore.** PMP also moved into `namespace RiscvISA` (`gem5::PMP` → `gem5::RiscvISA::PMP`) and gained `createDefaultFault(...)` for the `numRules==0` case.
- **H-extension two-stage (G-stage) translation** (`pagetable_walker.{cc,hh}` 19K→39K): `WalkType {OneStage,TwoStage,GstageOnly}`, second-stage state machine (`gstate`/`glevel`/`gpte`/`hgatp`), `walk()`/`walkOneStage()`/`walkTwoStage()`/`walkGStage()`, SATP-vs-VSATP selection via `misa.rvh && memaccess.virt`. **Inert unless `misa.rvh` is enabled** — safe to ignore for a plain Sv39 PIM thesis.
- **Address-translation mode plumbing** (`pagetable.{cc,hh}`): `AddrXlateMode` adds `SV57`; generalized `SV39_*` constants; new `getVPNFromVAddr(vaddr, mode)` honoring BARE/SV39/SV48/SV57 widths; `PTESv39` gains Svnapot `n` bit; `TlbEntry` gains guest `gpte` + `reset()`. **CAVEAT: the walk body is still hardcoded to 3 levels (`SV39_LEVELS`) with the SV39 canonical-MSB check — Sv48/Sv57 are NOT actually walked.**
- **Extended fault model** (`faults.{cc,hh}` + new `fault_codes.hh`): `ExceptionCode` extracted to its own header and extended with H-ext guest-page/virtual-instruction codes (INST/LOAD/STORE_GUEST_PAGE=20/21/23, VIRTUAL_INST=22, virtual-supervisor interrupt codes, INT_LOCAL_*); new `VirtualInstFault`.
- **TLB / MMU access-info refactor** (`tlb.{cc,hh}`, `mmu.hh`): new `MemAccessInfo` (priv/virt/force_virt/hlvx/lr + `bypassTLB()`) and `XlateStage`; `getMemPriv` retained but wrapped by `getMemAccessInfo`; `checkPermissions`/`createPagefault` signatures extended (H-ext args); `translateWithTLB`→`hiddenTranslateWithTLB`; new `getValidAddr()`; `RiscvFlags` alignment enum encodes LD/ST size in arch-flags bits 2:0; `pma` type `PMAChecker*`→`BasePMAChecker*`. **`mstatus.mprv` semantics preserved verbatim** — no FS data-access regression.
- **Modern FS boot path** (`RiscvFsWorkload.py`): new `RiscvBootloaderKernelWorkload` (bootloader + vmlinux + initrd + DTB + cmdline + panic/oops handling), backed by `arch/riscv/linux/fs_workload.hh BootloaderKernelWorkload`; workloads gain a `semihosting` param; `RiscvBareMetal` gains `auto_reset_vect`. **Recommended over hand-wiring `RiscvLinux`.** `RiscvBoard` exists in both trees.
- **Config/Resources API**: `Workload(id)` wrapper dropped in favor of `obtain_resource(resource_id, resource_version=...)` + `board.set_workload(...)` — pattern in `configs/example/gem5_library/riscv-ubuntu-run.py`.

**What you can build on:** a checkpoint-safe Sv39 FS boot of RISC-V Ubuntu 24.04 with PMP state preserved, a real machine-external interrupt path for `pim.wait` completion, and the modern bootloader workload — i.e. the FS baseline needed to compare SE fake-interrupt vs PLIC delivery (the mandated thesis trade-off).

## 5. Open questions to resolve before / during the port

**Decode / ISA / alignment**
- Are `pim.dispatch` target addresses guaranteed **8-byte aligned**? v25's `getAlignFlag()` imposes `MMU::DoubleWordAlign` on the 64-bit `Mem`; misalignment now faults via translation rather than the removed `STORE_ADDR_MISALIGNED`.
- Does `RiscvISA::ISA` still derive from `BaseISA` identically and does `getIsaPtr()`'s signature hold so the `static_cast`/`dynamic_cast` in the decoder graft and `pimComplete()` compile? (v25 `isa.hh:76` `class ISA : public BaseISA` looks intact — confirm at compile.)
- Should `pimNextToken` + `pimDone` be added to `serialize`/`unserialize`? Neither v23 nor v25 persists them; an FS checkpoint taken **mid-dispatch** would lose outstanding-token state on restore.
- Is `tc->quiesce()` + `IsQuiesce`/`IsSerializeAfter` wake-and-recheck (`NPC=PC`) behavior unchanged for the targeted-WFI model `pim.wait` relies on? (CPU-model surface beyond the decoder.)

**Glue / build / vendoring**
- Keep the PIMony SimObject class named `DRAMsim3` (fragile dual definition) or rename to `PIMony`? Renaming requires updating `sim_objects=` and the config `SimObject()` reference.
- Confirm the v25 build compiles **exactly one** of `PIMony.py` / `DRAMsim3.py` (HAVE_PIMONY xor HAVE_DRAMSIM3) to avoid duplicate-SimObject/duplicate-symbol errors.
- Is the early-`Return()` ordering in the merged `ext/dramsim3/SConscript` correct — does a missing PIMony dir **fall through** to DRAMsim3 detection rather than `Return()`ing?
- Does v25's main `SConstruct` still walk all `ext/*/SConscript` **before** `src/mem/SConscript` reads `env['HAVE_PIMONY']`? Neither tree seeds the flag with a default, so a changed walk order or strict KeyError checking would throw on the unset flag. Grep the v25 `SConstruct` ext-walk order.
- Will the PIMony ext (`pimony::GetMemorySystem` 4-string sig, `AddMACTransaction(addr,size,token)`) be re-vendored as `ext/dramsim3/PIMony` and build against v25's compiler unchanged? Rebuild `libdramsim3.so` from `CMakeLists.txt`; do the 2022-era fmt/spdlog pins compile on the v25 host toolchain or need a bump?
- Does the v25 RISC-V FS interrupt controller treat `postInterrupt(tid, 11, 0)` the same as SE mode, or does the index arg / machine-external delegation need adjustment for real PLIC/CLIC/APLIC?
- Re-grep the **whole** v25 `src/` for the literal `0x08000000` before finalizing `PIM_DISPATCH`, in case a later patch release filled the enum gap.
- In FS mode, confirm the address handed to `enqueuePIM` is a **physical** address after Sv39 translation + PMP, and that DRAMsim3/pimony (an `AbstractMemory` expecting PA) is mapped to a board mem range the walker covers and a PMA-uncacheable-compatible region (the dispatch is `UNCACHEABLE`). Confirm `pimony.cc` keys off `PIM_DISPATCH` on the post-translation packet and that v25 propagates the flag through to the mem side.

**FS-mode capability**
- Does the target RISC-V Linux image boot in **Sv39 or Sv48**? v25 walks only Sv39 (3 levels) despite the SV48/SV57 enum — force the kernel to Sv39 or extend the walk loop to a mode-driven level count. **Single biggest FS-mode gotcha.**
- Will the FS workflow use checkpoint/restore (to fast-forward past boot)? If yes, the v25 PMP serialize fix is **required**, not optional.
- Is the H extension (`misa.rvh`) ever enabled? If not, the two-stage/G-stage walker additions are dead code and can be ignored for review.
- Confirm `arch/riscv/linux/fs_workload.hh` (`BootloaderKernelWorkload`) and its SConscript are pulled when adopting `RiscvBootloaderKernelWorkload`.
- Inside `gem5-container`: is `GEM5_RESOURCE_DIR` set and does the container have network access to download the 24.04 image via `obtain_resource`?
- Does any existing PIM/CPU code call the **renamed** FS APIs (`PMAChecker*`→`BasePMAChecker*`, `gem5::PMP`→`gem5::RiscvISA::PMP`, `getMemPriv`→`getMemAccessInfo`, `translateWithTLB`→`hiddenTranslateWithTLB`, `startWalk`→`walk`, `pageFault(bool)`→`pageFault()`)? FS files are untouched, but grep the PIM instruction/CPU code for fallout before assuming zero.
